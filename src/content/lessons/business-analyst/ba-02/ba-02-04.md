> **Prerequisites:** *Functional vs non-functional requirements.* You should be able to tell a requirement from a solution and know that requirements must be measurable.

## Explanation

### Writing is a core BA skill

You can run excellent interviews and still fail if the requirements you write are ambiguous. Developers, testers and stakeholders all read your words and build, test and approve based on them. If a sentence can be read two ways, someone will pick the wrong one, and you will find out late and at cost.

The goal is simple: **anyone who reads the requirement should understand the same thing and be able to tell whether it has been met.**

### A reliable sentence pattern

Most functional requirements can be written with this pattern:

> **[Condition]** **[Actor]** **shall** **[action]** **[object]** **[measure or constraint]**.

| Part | Meaning | Example |
|---|---|---|
| Condition (optional) | When or in what situation | "When a payment is declined," |
| Actor | Who or what does it | "the system" / "a customer" |
| *shall* | Signals a mandatory requirement | "shall" |
| Action | One specific verb | "display" |
| Object | What is acted on | "the reason for the decline" |
| Measure or constraint (optional) | How, how fast, how many | "within 2 seconds" |

Result: *"When a payment is declined, the system shall display the reason for the decline within 2 seconds."*

**Use "shall" for mandatory, "should" for desirable, "may" for optional** and apply them consistently, since this makes priority visible in the text.

### The ten rules of a good requirement

1. **One requirement per statement.** Watch for *and*, *or*, *also*, and commas that join actions.
2. **Use active voice with a clear actor.** "The system shall email the customer" is clearer than "An email will be sent" (by whom?).
3. **Use precise verbs.** "Display", "calculate", "send", "store" are better than "handle", "support" or "process".
4. **Make it testable.** A tester must be able to say pass or fail.
5. **Quantify qualities.** Replace "fast", "many", "large" with numbers and units.
6. **Avoid ambiguous words.** Read the table below.
7. **Avoid design and technology** unless it is a real constraint.
8. **Keep it consistent.** Use the same term for the same thing everywhere (always "customer", never sometimes "client" and "user").
9. **Give each requirement a unique ID** so it can be referenced and traced.
10. **State the reason or source** where it is not obvious, such as "Source: refund policy v3".

### Words to challenge

| Word or phrase | Why it is risky | What to do |
|---|---|---|
| "fast", "quickly", "efficient" | Not measurable | Give a time or rate |
| "easy", "intuitive", "user-friendly" | Subjective | Define a task and time limit |
| "flexible", "scalable", "robust" | Vague | Say what must flex, scale or survive |
| "etc.", "and so on", "including but not limited to" | Open-ended list | List every item or reference a defined list |
| "as appropriate", "if necessary", "where possible" | Leaves the decision undefined | State the condition |
| "all", "never", "always" | Rarely true and hard to test | Check for exceptions |
| "support", "handle", "manage" | Hides the actual action | Use a specific verb |
| "he/she/it/they" | Unclear reference | Name the actor |
| "or" | Could mean either or both | Say which |

### Before and after

| Weak | Problem | Improved |
|---|---|---|
| "The system should handle large numbers of users quickly." | Vague quantity, speed and verb | "The system shall support 2,000 concurrent users with 95% of page loads under 2 seconds." |
| "Reports can be exported as needed." | "As needed" undefined | "A manager shall be able to export any report as CSV or PDF." |
| "The system will send an email." | Passive, no trigger or content | "When an order ships, the system shall email the customer a dispatch confirmation containing the tracking number." |
| "Users can log in and change their details and view orders." | Three requirements in one | Three separate requirements, each with its own ID |
| "Use dropdown menus for country." | Design | "The user shall select a country from the list of supported countries." |

### Other useful formats

**User story** (common in Agile):

> *As a* **[role]**, *I want* **[goal]** *so that* **[benefit]**.

*As a returning customer, I want to reuse my saved address so that checkout takes less time.* You will learn user stories fully in a later module.

**Acceptance criteria in Given-When-Then form** make a requirement testable:

> **Given** a logged-in customer with a saved address, **when** they reach the delivery step, **then** the saved address is pre-selected and can be changed.

### Reviewing your own requirements

Read each requirement as a **tester**: how would I check this? Then as a **developer**: could I build two different things that both satisfy it? If yes, it is ambiguous. Then as a **stakeholder**: does this match what I asked for?

A simple review checklist:

| Check | Question |
|---|---|
| Clear | Is there only one way to read it? |
| Atomic | Does it state a single thing? |
| Testable | Can I write a pass or fail test? |
| Necessary | Which need or goal does it support? |
| Feasible | Is it possible within time, cost and technology? |
| Consistent | Does it contradict another requirement or use different words for the same thing? |
| Traceable | Does it have an ID and a source? |

## Real-world examples

| Context | Poor requirement | Good requirement |
|---|---|---|
| **Insurance claim** | "The system shall process claims quickly." | "The system shall calculate and display the claim payout within 5 seconds of the handler submitting the claim form." |
| **E-commerce** | "Users can filter products." | "A customer shall be able to filter products by category, price range and rating, and the result list shall update in under 1 second." |
| **HR** | "Managers must approve leave when appropriate." | "When an employee submits a leave request, the system shall notify the line manager, who shall approve or reject it within 3 working days; if no decision is made, the system shall remind the manager." |
| **Healthcare** | "Records shall be secure and always available." | "Patient records shall be accessible only to authorised clinical staff, and every access shall be logged with user ID, date and time." |

## Step-by-step demonstration

**Scenario:** A library wants to improve how members reserve books. A stakeholder's notes say: *"Members need to be able to reserve books easily, get told when they arrive, and the librarian wants to see reservations and also the system should be quick and handle lots of members."*

**Step 1: Split the sentence into separate ideas.**
- Members reserve books.
- Members are told when books arrive.
- Librarian sees reservations.
- The system is quick.
- It handles lots of members.

**Step 2: Give each an actor, action and object.**
1. A member reserves a book that is currently on loan.
2. The system notifies the member.
3. The librarian views the list of reservations.

**Step 3: Add conditions and measures after asking questions.** Ask: *"How should members be told? How soon? How many reservations can a member hold? How many members use the service?"* Answers: email, within an hour, up to 5 reservations, about 3,000 members with at most 300 using the system at once.

**Step 4: Write the final requirements.**

| ID | Requirement | Source |
|---|---|---|
| LIB-01 | A logged-in member shall be able to reserve a book that is currently on loan. | Member survey |
| LIB-02 | The system shall limit each member to five active reservations. | Library policy |
| LIB-03 | When a reserved book is returned, the system shall email the member within 1 hour stating the pickup deadline. | Member survey |
| LIB-04 | A librarian shall be able to view all active reservations, sorted by date. | Librarian interview |
| LIB-05 | The system shall support 300 concurrent users with 95% of pages loading in under 2 seconds. | NFR workshop |

**Step 5: Add acceptance criteria for one.** LIB-02: *Given a member with five active reservations, when they try to reserve another book, then the system shall refuse the request and display the message "You have reached the limit of five reservations."*

**Step 6: Review as a tester.** For LIB-03 the tester asks: *"What if the member has no email?"* You find a gap, so you add LIB-06: *"If a member has no email address, the system shall add the notification to the librarian's call list."*

## Practical example

Rewrite each requirement so that it follows the rules in this lesson. Where information is missing, write the question you would ask, then make a sensible assumption.

1. "The app should be easy to use and have good performance."
2. "Customers can see their orders and cancel them and download invoices."
3. "The system will notify users when appropriate."
4. "Use a blue button for checkout."
5. "Support all browsers."

*Hint for 5:* Ask which browsers and versions matter, using usage data. Then write: "The website shall work on the latest two versions of Chrome, Edge, Firefox and Safari."

## Common mistakes

1. **Writing in a rush and fixing later.** Ambiguity found in testing costs far more than a few minutes of care now.
2. **Using different words for the same thing.** Customer, client, user and account holder may be four different people to a reader.
3. **Assuming the reader knows what you know.** Define terms in a glossary and avoid unexplained abbreviations.
4. **Over-specifying.** Describing every pixel and database field in a requirement limits the team without adding value. Match detail to risk.
5. **Hiding conditions in long paragraphs.** Put the condition at the start of the sentence, or use a table or Given-When-Then.
6. **Never reading it aloud or asking a tester.** A five-minute review by someone who will test it finds most problems.
