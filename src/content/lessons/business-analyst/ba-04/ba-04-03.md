> **Prerequisites:** ba-04-02 Business Requirements Document (BRD)

## Explanation

### From business need to system behaviour

The BRD says *"Patients shall be able to book appointments online."* That's not enough for a developer. Which fields? What if the slot is taken? What does the confirmation say? The **Functional Requirements Document (FRD)** answers these questions by describing **exactly what the system must do**, without prescribing how it's coded.

```
BRD:  BR-01 Patients shall book appointments online 24/7
          │
FRD:  FR-01 Patient searches available slots by clinic, date and clinician
      FR-02 System shows only slots not already booked
      FR-03 Patient selects a slot and confirms
      FR-04 System sends confirmation email within 5 minutes
      FR-05 If the slot was taken meanwhile, system shows message and alternatives
```

### Standard FRD structure

| # | Section | Contents |
|---|---|---|
| 1 | Document control | Version, change log, approvals |
| 2 | Introduction | Purpose, scope, references to the BRD |
| 3 | System overview | Context diagram: users and connected systems |
| 4 | User roles and permissions | Who can do what |
| 5 | Functional requirements | Grouped by feature or use case, each with ID, description, priority, BRD trace |
| 6 | Use cases / user flows | Step-by-step interactions, including alternate and exception paths |
| 7 | Business rules and validations | Field rules, calculations, conditions |
| 8 | Data requirements | Entities, fields, formats, data dictionary |
| 9 | Screens / wireframes | Layouts, fields, actions (illustrative) |
| 10 | Reports and notifications | Content, triggers, recipients |
| 11 | Interfaces | Data exchanged with other systems (what, not how) |
| 12 | Open issues | Questions still to resolve |

### Use cases: the heart of many FRDs

A **use case** describes how a user (actor) interacts with the system to achieve a goal.

| Element | Example |
|---|---|
| **ID / Name** | UC-03 Book appointment |
| **Actor** | Patient |
| **Preconditions** | Patient is logged in |
| **Main flow** | 1. Patient selects clinic and date. 2. System shows available slots. 3. Patient chooses a slot. 4. System asks for reason for visit. 5. Patient confirms. 6. System books slot and sends confirmation. |
| **Alternate flow** | 3a. No slots available: system offers next available date. |
| **Exception flow** | 5a. Slot taken by another patient before confirming: system shows message and returns to step 2. |
| **Postconditions** | Appointment saved; slot unavailable to others; confirmation sent. |
| **Business rules** | BRULE-01 max 2 future appointments per patient |

### Data dictionary

Defines every data field so there's no confusion.

| Field | Type | Length | Required | Validation | Example |
|---|---|---|---|---|---|
| Date of birth | Date | | Yes | Not in future; age 0-120 | 1990-04-12 |
| Mobile number | Text | 15 | No | UK format, starts 07 or +447 | 07700 900123 |
| Reason for visit | Text | 250 | Yes | Free text | Follow-up blood test |

| Managers approve leave | Approver = line manager in HR system; delegation when manager on leave; auto-escalation after 5 working days |

## Step-by-step demonstration

**Scenario:** Turning BR-03 (*"Members shall join a waitlist for full classes"*) into FRD content.

**Step 1: Identify actors.** Member, system, instructor (sees waitlist).

**Step 2: Write the main flow.**
1. Member views a full class.
2. System shows "Join waitlist" and the current waitlist position.
3. Member joins.
4. System confirms position by email.

**Step 3: Ask "what if?" for alternates and exceptions.**
- What if a booked member cancels? → *System offers the place to waitlist position 1 by email; they have 2 hours to accept, then it goes to position 2.*
- What if the class starts in less than 2 hours? → *Place goes to the first waitlisted member automatically.*
- Can a member be on many waitlists? → *Max 3 (business rule).*

**Step 4: Write numbered functional requirements.**

| ID | Requirement | Trace |
|---|---|---|
| FR-20 | The system shall display a Join waitlist option when a class is full | BR-03 |
| FR-21 | The system shall show the member's waitlist position | BR-03 |
| FR-22 | When a place is released, the system shall offer it to the first waitlisted member by email and SMS | BR-03 |
| FR-23 | If the offer isn't accepted within 2 hours, the system shall offer it to the next member | BR-03 |
| FR-24 | Less than 2 hours before class, the system shall auto-book the first waitlisted member | BR-03 |
| FR-25 | A member shall be on at most 3 waitlists at a time | BRULE-03 |

**Step 5: Add data and notifications.** Define the waitlist entry fields (member ID, class ID, position, joined timestamp, status) and the email/SMS templates.

## Practical example

Write exception flows for *"Customer pays for an order by card"*:

- Card declined → show message, keep basket, let customer try another card.
- Payment provider timeout → do not create the order; show "Payment not completed, you have not been charged"; log the error.
- 3D Secure check failed → treat as declined.
- Customer closes browser after payment but before confirmation → order still created; confirmation emailed.

## Common mistakes

1. **Only the happy path.** Most defects hide in alternate and exception flows.
2. **Design dressed as requirements.** "Use a modal popup" is design; "confirm before deleting" is the requirement.
3. **No trace to the BRD.** Every FR should link to a business requirement.
4. **Undefined data.** Vague fields like "address" cause integration problems; use a data dictionary.
5. **Wireframes treated as final designs.** Label them illustrative unless the layout is a requirement.
