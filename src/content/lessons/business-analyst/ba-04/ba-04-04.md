> **Prerequisites:** ba-04-03 Functional Requirements Document (FRD)

## Explanation

### The most complete requirements document

A **Software Requirements Specification (SRS)** is a comprehensive description of a software system: everything it must do (functional), how well it must do it (non-functional), the interfaces it must support, and the constraints it must respect. It's the document a development team or vendor can build and test against.

The best-known structure comes from **IEEE 830** (now superseded by ISO/IEC/IEEE 29148, which keeps a similar outline).

### Typical SRS outline (IEEE-style)

```
1. Introduction
   1.1 Purpose
   1.2 Scope
   1.3 Definitions, acronyms, abbreviations
   1.4 References
   1.5 Overview of the document
2. Overall description
   2.1 Product perspective (context, connected systems)
   2.2 Product functions (summary)
   2.3 User classes and characteristics
   2.4 Operating environment
   2.5 Design and implementation constraints
   2.6 Assumptions and dependencies
3. Specific requirements
   3.1 External interface requirements (user, hardware, software, communications)
   3.2 Functional requirements (by feature)
   3.3 Non-functional requirements (performance, security, reliability, usability...)
   3.4 Data requirements
4. Appendices (analysis models, glossary, to-be-determined list)
```

### How the SRS differs from the FRD

| | FRD | SRS |
|---|---|---|
| Focus | Functional behaviour | Functional **and** non-functional, interfaces, constraints |
| Audience | Business and IT | Mainly developers, architects, testers, vendors |
| Detail | Detailed functions | Complete and precise enough to build and test |
| Often used for | Internal agreement | Contracts with vendors, regulated systems |

In many companies a single **FRS/SRS** covers both.

### Interface requirements

Describe **what** must be exchanged with other systems, not the code.

| ID | Interface | Direction | Data | Frequency | Rule |
|---|---|---|---|---|---|
| IF-01 | Patient record system | Inbound | Patient ID, name, DOB, NHS number | Real time on login | Patient must exist in the record system |
| IF-02 | SMS gateway | Outbound | Mobile number, message text | Event-driven | Max 160 characters |
| IF-03 | Finance system | Outbound | Daily no-show fees | Nightly batch at 02:00 | CSV, one row per fee |

### NFRs in an SRS

Each NFR gets an ID, measurable target and verification method.

| ID | Category | Requirement | Verification |
|---|---|---|---|
| NFR-01 | Performance | 95% of slot searches return in < 2 s with 500 concurrent users | Load test |
| NFR-02 | Availability | 99.5% monthly, excluding planned maintenance Sun 01:00-03:00 | Monitoring reports |
| NFR-03 | Security | All patient data encrypted in transit (TLS 1.2+) and at rest | Security test, config review |
| NFR-04 | Accessibility | WCAG 2.2 AA | Accessibility audit |
| NFR-05 | Data retention | Appointment records kept 8 years then deleted | Process review |

### Open items (To Be Determined) list

Unknowns are normal. List them explicitly with an owner and due date rather than hiding them.

| Open item | Owner | Due |
|---|---|---|
| Max number of clinicians per clinic | Ops manager | 15 March |
| SMS provider choice | IT procurement | 30 March |

## Real-world examples

| Context | Why an SRS was essential |
|---|---|
| Vendor building a ticketing platform | The SRS was attached to the contract; acceptance testing was done against it |
| Medical device software | Regulators require a complete, traceable specification |
| Replacing a legacy banking module | Interfaces with 12 other systems had to be specified exactly |

## Step-by-step demonstration

**Scenario:** Producing SRS content for the clinic booking system after the BRD and FRD.

**Step 1: Introduction.** Purpose (specify the online booking system for vendor build), scope (booking, cancellation, reminders; excludes video consultation), definitions (e.g. *slot*, *no-show*).

**Step 2: Overall description.** Context diagram: patients (web/mobile browser), reception staff, patient record system, SMS gateway, email service, finance system.

```
 Patient ──► [ Booking System ] ◄── Reception
               │     │     │
     Patient record  SMS   Finance
        system     gateway  system
```

User classes: patients (varied digital skills, many over 65), reception (daily heavy users), admin (configures clinics and slots).

Constraints: must use the organisation's single sign-on for staff; hosted in UK data centres.

**Step 3: Functional requirements.** Import from the FRD, grouped by feature (search, book, cancel, waitlist, reminders, admin).

**Step 4: Interfaces.** IF-01 to IF-03 as in the table above.

**Step 5: NFRs.** Performance, availability, security, accessibility, retention, audit logging, browser support.

**Step 6: Appendices.** Glossary, open items list, use case diagrams, data model.

**Step 7: Review.** Walk through with the vendor's architect and test lead; resolve questions; baseline v1.0.

## Practical example

Turn these informal notes into SRS-style requirements:

| Note | SRS requirement |
|---|---|
| "Has to work for lots of people Monday morning" | NFR-06 The system shall support 2,000 concurrent users with 95% of pages loading in under 3 s |
| "Pull patient details from our records" | IF-01 On login, the system shall retrieve patient name, DOB and NHS number from the patient record system in real time |
| "Keep a log for audits" | NFR-07 The system shall log every booking change with user, timestamp, old and new values, retained for 8 years |

## Common mistakes

1. **Copying a template without tailoring.** Delete sections that don't apply; add what's missing.
2. **Unmeasurable NFRs.** Every NFR needs a target and a way to verify it.
3. **Hidden unknowns.** Keep an explicit open items list.
4. **Specifying code-level design.** Describe interfaces by data and behaviour, not classes and tables, unless constrained.
5. **No traceability.** The SRS should link back to BRD/FRD and forward to tests.
