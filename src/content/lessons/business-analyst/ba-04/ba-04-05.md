> **Prerequisites:** ba-04-04 Software Requirements Specification (SRS)

## Explanation

### Following the thread

A **Requirements Traceability Matrix (RTM)** is a table that links each requirement to where it came from and where it goes: business objective → requirement → design → build → test. It answers questions like:

- *Is every business requirement covered by at least one test?*
- *Why does this feature exist?*
- *If this requirement changes, what else is affected?*

```
 Business objective ─► Business req ─► Functional req ─► Design / Story ─► Test case ─► Result
    (why)              (BRD)            (FRD/SRS)        (Jira)             (test plan)
         ◄──────────────── backward traceability ────────────────
         ──────────────── forward traceability  ────────────────►
```

### Forward and backward traceability

| Direction | Question | Catches |
|---|---|---|
| **Forward** | Is every requirement designed, built and tested? | Missing features, untested requirements |
| **Backward** | Does every feature/test trace to a real requirement? | Gold plating, scope creep |
| **Bidirectional** | Both | Both problems |

### A simple RTM

| BR ID | Business requirement | FR ID | Functional requirement | Story | Test case | Status |
|---|---|---|---|---|---|---|
| BR-01 | Book appointments online | FR-01 | Search slots by clinic and date | APP-12 | TC-01, TC-02 | Passed |
| BR-01 | | FR-02 | Show only free slots | APP-13 | TC-03 | Passed |
| BR-01 | | FR-05 | Handle slot taken during booking | APP-15 | TC-07 | Failed |
| BR-02 | Cancel online | FR-08 | Cancel up to 24h before | APP-20 | TC-10 | Not run |
| BR-03 | Reminders | FR-12 | SMS 24h before | APP-25 | (none) | ⚠ No test |

Problems are visible at a glance: BR-03 has no test, and FR-05 failed.

### Common RTM columns

- Requirement ID and description
- Source (stakeholder, document, regulation)
- Priority (MoSCoW)
- Parent (higher-level requirement)
- Design/story reference
- Test case IDs
- Test status
- Owner, version, change history

### Using the RTM for impact analysis

When someone asks to change a requirement, the RTM shows everything linked to it.

> *Change: cancellation window from 24h to 12h.*
> RTM shows: FR-08 → stories APP-20, APP-21 → tests TC-10, TC-11 → business rule BRULE-01 → finance interface IF-03 (no-show fees).
> Impact: 2 stories, 2 tests, 1 rule, 1 interface. Estimate effort before approving.

### Tools

- **Spreadsheet**: fine for small projects
- **Jira + test plugin (Xray, Zephyr)**: links stories to test cases automatically
- **Requirements tools (Jama, Polarion, DOORS)**: for large or regulated projects

## Real-world examples

| Context | How the RTM helped |
|---|---|
| Pharmaceutical system audit | Auditor asked for proof that every regulatory requirement was tested; the RTM provided it in minutes |
| Bank migration | Backward tracing found 40 report fields nobody used; they were dropped, saving weeks |
| E-commerce release | Forward tracing found that the returns policy change had no test; caught before go-live |

## Step-by-step demonstration

**Scenario:** Building an RTM for the gym booking project.

**Step 1: List business requirements** from the BRD: BR-01 book online, BR-02 cancel online, BR-03 waitlist, BR-04 instructor attendee list.

**Step 2: Link functional requirements** from the FRD under each BR (FR-01 to FR-25).

**Step 3: Add stories.** Each FR maps to one or more Jira stories.

**Step 4: Add test cases** as testers write them.

**Step 5: Review gaps.**
- Forward check: FR-24 (auto-book within 2 hours) has no test → ask testers to add TC-30.
- Backward check: story GYM-44 "Add class photos" traces to nothing → raise with Product Owner; moved to a future backlog.

**Step 6: Update during testing.** Status column shows Passed/Failed/Not run. Before go-live, every Must requirement shows Passed.

**Step 7: Use it for change.** A request to raise max bookings from 3 to 5 → RTM shows BRULE-01, FR-04, GYM-08, TC-05, TC-06 are affected.

Look at this RTM extract and find the issues:

| BR | FR | Story | Test | Status |
|---|---|---|---|---|
| BR-01 | FR-01 | S-10 | T-01 | Passed |
| BR-01 | FR-02 | S-11 | | |
| BR-02 | FR-03 | S-12 | T-04 | Failed |

Issues: FR-02 has no test (forward gap). FR-03 failed testing (not ready). S-13 has no parent requirement (backward gap: possible gold plating or missing requirement).

## Common mistakes

1. **Building the RTM at the end.** Create it as requirements are written; it's useless as an afterthought.
2. **Never updating it.** A stale RTM gives false confidence.
3. **Too many columns.** Track what you'll actually use.
4. **Only forward tracing.** Backward tracing catches unnecessary work.
5. **Treating it as paperwork.** Use it actively for test coverage and impact analysis.
