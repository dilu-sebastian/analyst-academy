## Explanation

### A picture really is worth a thousand words

Read this: *"When a customer submits a claim, an agent checks it. If the amount is under £500 and documents are complete, the agent approves it and finance pays within 3 days. Otherwise, it goes to a senior assessor, who may request more documents, approve or reject. Rejected claims can be appealed once."*

Now look at the same thing as a diagram:

```
[Claim submitted] → [Agent checks] → <Under £500 and complete?>
                                        │yes                 │no
                                        ▼                    ▼
                                  [Agent approves]    [Senior assessor reviews]
                                        │              │approve │reject │need docs
                                        ▼              ▼        ▼       ▼
                                  [Finance pays ≤3d]◄──┘   [Reject] [Request docs]
                                                             │
                                                        <Appeal?> → ...
```

The diagram makes the decision points, paths and gaps obvious. (Did you notice the text never said what happens after documents are requested?)

**Modelling** means creating simplified visual representations of processes, systems, data or interactions to understand, communicate and analyse them.

### Why BAs model

| Benefit | Explanation |
|---|---|
| **Shared understanding** | Everyone looks at the same picture instead of imagining different ones |
| **Finds gaps** | Missing steps, dead ends and undefined decisions become visible |
| **Simplifies complexity** | Hides irrelevant detail, shows what matters |
| **Speeds up validation** | Stakeholders spot errors in a diagram faster than in text |
| **Bridges languages** | Business and technical people can both read a good diagram |
| **Supports analysis** | Find bottlenecks, handoffs, duplication and automation opportunities |

### The main model types a BA uses

| Model | Shows | Covered in |
|---|---|---|
| **Flowchart / process flow** | Steps and decisions in a process | ba-05-02 |
| **Use case diagram** | Actors and the goals they achieve with a system | ba-05-03 |
| **Activity diagram (UML)** | Detailed flow of activities, including parallel work | ba-05-04 |
| **Sequence diagram (UML)** | Messages between actors and systems over time | ba-05-05 |
| **BPMN** | Business processes across roles with standard notation | ba-06 |
| **Context diagram** | The system and everything it connects to | ba-04-04 |
| **Data model / ERD** | Entities and relationships in data | Optional |
| **Wireframe** | Screen layouts | Optional |

### UML in one paragraph

**UML (Unified Modeling Language)** is a standard set of diagram types maintained by the Object Management Group (OMG). It has 14 diagram types, but BAs mainly use three: **use case**, **activity** and **sequence** diagrams. Using a standard notation means anyone trained in UML reads your diagram the same way.

### Choose the right level of detail

```
High level           Medium                      Detailed
Context diagram  →   Process flow / Use cases →  Activity / Sequence diagrams
(for executives)     (for business users)        (for developers and testers)
```

## Real-world examples

| Situation | Model used | Result |
|---|---|---|
| Insurer redesigning claims | As-is process flow on a wall | Found that claims passed between 7 teams; reduced to 3 |
| Bank API integration | Sequence diagram | Developers spotted a missing timeout response before coding |
| New HR portal | Use case diagram | Scope agreed in one meeting: 12 use cases in, 4 out |
| Hospital discharge | Activity diagram with swimlanes | Showed pharmacy as a bottleneck; parallel steps introduced |

## Step-by-step demonstration

**Scenario:** A coffee shop owner explains how mobile orders work. You decide which models to produce.

**Step 1: Ask what you need to understand or communicate.**
- The owner wants to see the overall flow → **process flow**
- The developer needs to know what customers and staff can do in the app → **use case diagram**
- The payment integration needs detail → **sequence diagram**

**Step 2: Sketch the process flow** with the owner on a whiteboard in 15 minutes: order placed → payment → barista notified → drink made → customer notified → collected.

**Step 3: Ask gap questions the diagram reveals.**
- What if payment fails?
- What if the customer doesn't collect within 30 minutes?
- What if an item is out of stock after ordering?

**Step 4: Refine and share.** Draw cleanly in a tool (draw.io, Lucidchart, Visio, Miro), add the answers, and send for confirmation.

## Practical example

For each need, choose a model:

| Need | Model |
|---|---|
| Explain to executives which systems the new CRM connects to | Context diagram |
| Agree with stakeholders what users can do in a new portal | Use case diagram |
| Show how an order moves between sales, warehouse and finance | Process flow / BPMN with swimlanes |
| Show the exact messages between app, payment provider and bank | Sequence diagram |
| Show parallel steps in onboarding a new employee | Activity diagram |

## Common mistakes

1. **Diagrams that are too detailed.** If it doesn't fit on one page, split it into levels.
2. **Inventing notation.** Use standard symbols or include a legend.
3. **Modelling alone.** Diagrams built with stakeholders are more accurate and better accepted.
4. **Only the happy path.** Show decisions and exceptions.
5. **Pretty but wrong.** Validate the content before polishing the look.
