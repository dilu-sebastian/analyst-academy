## Explanation

### The simplest, most useful diagram

A **flowchart** shows the steps in a process in order, including decisions. A **process flow** (or process map) is the same idea applied to a business process, often split by who does each step. They're quick to draw, easy for anyone to read and perfect for workshops.

### Core symbols

| Symbol | Shape | Meaning | Example |
|---|---|---|---|
| **Terminator** | Rounded rectangle / oval | Start or end | "Customer places order" / "Order delivered" |
| **Process / activity** | Rectangle | A step or task | "Check stock" |
| **Decision** | Diamond | A yes/no or multi-way question | "In stock?" |
| **Arrow (flow line)** | → | Direction of flow | |
| **Document** | Rectangle with wavy base | A document produced or used | "Invoice" |
| **Data / input-output** | Parallelogram | Data entered or output | "Enter card details" |
| **Connector** | Small circle | Links to another part of the diagram | "A" |

In text form in this lesson we'll write: `( )` start/end, `[ ]` step, `< >` decision.

### Swimlanes: who does what

A **swimlane (cross-functional) flowchart** divides the diagram into lanes, one per role, team or system. It instantly shows handoffs, which is where delays and errors usually happen.

```
Customer   | (Start)→[Submit return request]                          [Ship item]→
-----------+--------------------------------------------------------------------
System     |                 →[Generate label]→[Email label]→
-----------+--------------------------------------------------------------------
Warehouse  |                                                    →[Receive & inspect]→<OK?>→
-----------+--------------------------------------------------------------------
Finance    |                                                                     yes→[Refund]→(End)
```

### Rules for clean process flows

1. **One start, clear end(s).**
2. **Verb-noun labels** for steps: "Check stock", not "Stock".
3. **Questions in decisions**, with every exit labelled ("Yes"/"No").
4. **Flow left-to-right or top-to-bottom.** Avoid crossing lines.
5. **One level of detail per diagram.** Link to a sub-process for detail.
6. **Every path ends somewhere.** No dead ends.

### Analysing a process flow

Once the as-is flow is drawn, look for:

| Look for | Example | Possible improvement |
|---|---|---|
| **Handoffs** | Order passes between 4 teams | Reduce or automate handoffs |
| **Waiting** | Approval waits 3 days in a queue | Set SLAs, delegate, auto-approve low risk |
| **Rework loops** | Forms sent back for missing data | Validate at entry |
| **Duplication** | Data typed into 2 systems | Integrate systems |
| **Manual steps** | Copy-paste from email | Automate |
| **Unclear ownership** | No lane owns "chase supplier" | Assign an owner |

## Real-world examples

| Organisation | What the flow revealed |
|---|---|
| Car rental | Damage checks happened twice (at return desk and in the yard); one was removed |
| University admissions | Applications waited in a shared inbox for 5 days before anyone opened them |
| Online retailer | Returns had a rework loop: 30% sent back for missing order numbers; a form field fixed it |

## Step-by-step demonstration

**Scenario:** Map the as-is process for a small company's purchase requests.

**Step 1: Gather facts.** From interviews: An employee emails a request to their manager. The manager approves by reply email. The employee forwards approval to purchasing. Purchasing checks the budget with finance by email. If budget is available, purchasing raises a purchase order (PO) and sends it to the supplier. If not, the request is rejected.

**Step 2: Identify lanes.** Employee, Manager, Purchasing, Finance, Supplier.

**Step 3: Draw the flow.**

```
Employee   | (Need item)→[Email request]                →[Forward approval]
Manager    |               →[Review]→<Approve?>─no→[Reply reject]→(End)
           |                           yes→[Reply approve]─┘
Purchasing |                                       →[Ask finance re budget]   →<Budget?>─yes→[Raise PO]→
Finance    |                                              →[Check budget]→[Reply]┘     no→[Reject]→(End)
Supplier   |                                                                                     →[Receive PO]→(End)
```

**Step 4: Analyse.** 4 handoffs by email; employee manually forwards (error-prone); finance check adds 2 days; no tracking.

**Step 5: Propose a to-be flow.** Request submitted in a form → auto-routed to manager → on approval, budget checked automatically against the finance system → PO generated. Handoffs drop from 4 email steps to 1 approval.

## Practical example

Fix this badly drawn flow:

```
[Start] → [Stock] → <?> → [Ship]
```

Problems: start not a terminator; "Stock" isn't a verb-noun; decision has no question and unlabelled exits; no path for "no"; no end.

Fixed:

```
(Order received) → [Check stock] → <Item in stock?> ─yes→ [Ship order] → (Order shipped)
                                         └─no→ [Notify customer of delay] → (Awaiting stock)
```

## Common mistakes

1. **Mixing as-is and to-be** in one diagram. Draw them separately.
2. **Drawing the official process,** not the real one. Validate with the people who do the work.
3. **Unlabelled decision exits.** Readers can't tell which path is which.
4. **Too much on one page.** Use sub-processes.
5. **No owner for steps.** Use swimlanes so responsibility is clear.
