> **Prerequisites:** ba-05-02 Flowcharts and process flows

## Explanation

### Who uses the system, and for what?

A **use case diagram** is a UML diagram that shows the **actors** who interact with a system and the **use cases** (goals) they achieve with it. It is a one-page picture of a system's functional scope.

It does **not** show the order of steps or the detail. That goes in the written use case (see ba-04-03) or an activity diagram.

### Elements

| Element | Notation | Meaning |
|---|---|---|
| **Actor** | Stick figure (or box labelled «actor» for systems) | A role (not a named person) or external system that interacts with the system |
| **Use case** | Oval with a verb-noun name | A goal the actor achieves, e.g. "Book appointment" |
| **System boundary** | Rectangle around use cases | What's inside the system's scope |
| **Association** | Line between actor and use case | The actor takes part in the use case |
| **«include»** | Dashed arrow from base to included use case | The base use case **always** uses the included one |
| **«extend»** | Dashed arrow from extending to base use case | Optional behaviour that **sometimes** adds to the base |
| **Generalisation** | Solid line with hollow triangle | A specialised actor or use case inherits from a general one |

### A text sketch

```
                 ┌──────────── Clinic Booking System ────────────┐
                 │                                                │
  Patient ───────┼──( Register )                                  │
     │           │                                                │
     ├───────────┼──( Book appointment ) ┄┄«include»┄┄► ( Log in )│
     │           │          ▲                                     │
     │           │          ┆ «extend»                            │
     │           │   ( Join waitlist )                            │
     ├───────────┼──( Cancel appointment ) ┄┄«include»┄┄► (Log in)│
     │           │                                                │
  Receptionist ──┼──( Book on behalf of patient )                 │
     │           │                                                │
  Admin ─────────┼──( Manage clinic schedules )                   │
                 │                                                │
                 │  ( Send reminder ) ───────────────────────── SMS Gateway «system»
                 └────────────────────────────────────────────────┘
```

### Include vs extend

| | «include» | «extend» |
|---|---|---|
| When | Always happens as part of the base | Happens only under certain conditions |
| Arrow direction | Base → included | Extension → base |
| Example | "Book appointment" includes "Log in" | "Join waitlist" extends "Book appointment" (only when the slot is full) |
| Use for | Reusing common steps | Optional or exceptional behaviour |

Tip: don't overuse them. Many good diagrams use neither.

### Primary and secondary actors

- **Primary actors** start a use case to achieve their goal (Patient books an appointment). Usually drawn on the left.
- **Secondary (supporting) actors** help the system deliver it (SMS gateway sends the reminder). Usually drawn on the right.

### Naming use cases

Use **verb + noun** from the actor's point of view, describing a meaningful goal:

| Weak | Better |
|---|---|
| Database | Search products |
| Login screen | Log in |
| Click submit | Place order |
| Manage everything | Manage user accounts |

## Real-world examples

| System | Actors | Sample use cases |
|---|---|---|
| ATM | Customer, Bank system, Technician | Withdraw cash, Check balance, Deposit cheque, Refill cash |
| Online shop | Shopper, Guest, Admin, Payment provider | Browse products, Place order, Track order, Manage catalogue |
| HR portal | Employee, Manager, HR admin | Request leave, Approve leave, Update personal details, Run headcount report |

## Step-by-step demonstration

**Scenario:** Draw a use case diagram for a gym's online class booking system.

**Step 1: Identify actors.** Ask: *Who uses it? Who maintains it? What other systems does it talk to?*
- Member, Instructor, Gym manager, Email/SMS service.

**Step 2: List goals for each actor.**
- Member: view timetable, book class, cancel booking, join waitlist, view booking history.
- Instructor: view attendee list, mark attendance.
- Gym manager: manage timetable, view attendance reports.
- Email/SMS service: (supports) send notifications.

**Step 3: Draw the boundary** and place use cases inside, actors outside.

**Step 4: Add relationships.**
- "Book class" «include» "Log in".
- "Join waitlist" «extend» "Book class" (condition: class full).
- "Send notification" associated with the Email/SMS service.

**Step 5: Check scope.** Is "Pay for class" in scope? The BRD says payments are out of scope, so it's not on the diagram. Write it in a note: *Out of scope: payments, personal training.*

**Step 6: Validate** with the gym manager and an instructor. The instructor asks for "Cancel class" (e.g. when ill). Add it, associated with Instructor and Gym manager, and note that it triggers notifications.

## Practical example

What's wrong with this diagram description?

> Actors: "Sarah", "Database". Use cases: "Login screen", "Click buy", "Stuff for admin". «include» arrow from "Pay" to "Apply discount code".

| Problem | Fix |
|---|---|
| "Sarah" is a person, not a role | Use a role: "Customer" |
| "Database" is internal, not an actor | Remove; only external systems are actors |
| Use case names are screens or clicks | "Log in", "Place order", "Manage products" |
| Discount codes are optional | Use «extend» from "Apply discount code" to "Pay" |

## Common mistakes

1. **Treating it as a flowchart.** Use case diagrams don't show sequence.
2. **Too many tiny use cases.** "Enter name", "Enter address" are steps, not goals.
3. **Named people as actors.** Use roles.
4. **Overusing include/extend.** Use them only when they add clarity.
5. **No written detail.** The diagram is a summary; each important use case still needs a written description.
