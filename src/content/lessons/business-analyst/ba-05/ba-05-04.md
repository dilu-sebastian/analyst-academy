## Explanation

### Flowcharts with superpowers

A **UML activity diagram** shows the flow of activities in a process or use case. It looks like a flowchart but adds standard notation for **parallel work**, **merging paths** and **swimlanes (partitions)**. BAs use it to detail a use case or a business workflow precisely.

### Elements

| Element | Notation | Meaning |
|---|---|---|
| **Initial node** | ● filled circle | Where the flow starts |
| **Activity / action** | Rounded rectangle | A step, e.g. "Validate order" |
| **Control flow** | → arrow | Order of actions |
| **Decision node** | ◇ diamond with guarded exits `[in stock]` `[out of stock]` | Choose one path based on a condition |
| **Merge node** | ◇ diamond with several inputs, one output | Alternative paths come back together |
| **Fork** | ━ thick bar, one input, many outputs | Start parallel activities |
| **Join** | ━ thick bar, many inputs, one output | Wait until all parallel activities finish |
| **Activity final** | ◉ bullseye | The whole activity ends |
| **Flow final** | ⊗ circle with X | One path ends, others continue |
| **Partition (swimlane)** | Vertical/horizontal lanes | Who performs each action |

**Guards** are conditions in square brackets on decision exits: `[amount > 500]`, `[else]`.

### Decision vs fork

This is the key difference from a basic flowchart:

| Decision ◇ | Fork ━ |
|---|---|
| **One** path is taken | **All** paths are taken at the same time |
| "Either A or B" | "A and B in parallel" |
| Closed by a **merge** | Closed by a **join** (waits for all) |

### Example: online order fulfilment

```
●
│
(Receive order)
│
◇──[payment failed]──►(Notify customer)──►◉
│[payment ok]
━━━━━━━━━━━━━━━━━━━━━━  fork
│                   │
(Pick & pack items) (Send confirmation email)
│                   │
━━━━━━━━━━━━━━━━━━━━━━  join
│
(Ship order)
│
◉
```

Picking and emailing happen in parallel; shipping only starts when both are done.

## Real-world examples

| Process | Why an activity diagram helped |
|---|---|
| New employee onboarding | IT setup, HR paperwork and desk allocation run in parallel; the join showed the start date depended on the slowest (IT laptop, 5 days) |
| Loan application | Guards made credit rules explicit: `[score ≥ 700]`, `[600-699]` → manual review, `[< 600]` → reject |
| Hospital discharge | Pharmacy and transport booking could run in parallel instead of in sequence, saving 2 hours per patient |

## Step-by-step demonstration

**Scenario:** Model the "Process expense claim" workflow with partitions.

**Step 1: List actions.** Submit claim, validate receipts, approve (manager), approve (finance manager if > £2,000), pay, notify employee, record in ledger.

**Step 2: Identify decisions and guards.**
- Receipts valid? `[valid]` / `[invalid]`
- Manager decision: `[approved]` / `[rejected]`
- Amount: `[> £2,000]` / `[else]`

**Step 3: Identify parallel work.** After payment, "Notify employee" and "Record in ledger" can happen in parallel.

**Step 4: Draw with partitions.**

```
Employee      | ● → (Submit claim)                                      ◄────── (Receive notification)
System        |        → (Validate receipts) → ◇ [invalid] → (Return to employee) → ⊗
              |                                 [valid] ↓
Manager       |                              (Review claim) → ◇ [rejected] → (Notify rejection) → ◉
              |                                                [approved] ↓
System        |                                                ◇ [> £2,000] → Finance manager (Approve) ─┐
              |                                                [else] ──────────────────────────────────►◇ merge
Finance       |                                                                                (Pay claim)
              |                                                                                ━━ fork ━━
              |                                                                    (Notify employee) (Record in ledger)
              |                                                                                ━━ join ━━ → ◉
```

**Step 5: Validate.** Walk through three claims (valid small, valid large, missing receipt) on the diagram with finance. They confirm and add: *rejected claims can be resubmitted once*, so you add a loop.

## Practical example

Decide: decision or fork?

| Situation | Notation |
|---|---|
| If the customer is a member, apply a discount; otherwise charge full price | Decision |
| After a sale, update stock and send a receipt at the same time | Fork / join |
| Background check and reference check run simultaneously before an offer | Fork / join |
| Route support ticket to billing or technical team based on category | Decision |

## Common mistakes

1. **Using a decision when activities are parallel** (or vice versa). Ask: does one path happen, or all?
2. **Forgetting the join.** Without it, it's unclear whether the next step waits for all parallel work.
3. **Missing guards.** Every decision exit needs a condition, and they must not overlap.
4. **Overlapping conditions** like `[> 500]` and `[≥ 500]`. Make guards mutually exclusive.
5. **Too much detail.** Model business actions, not every click.
