## Explanation

### Who says what to whom, and when

A **UML sequence diagram** shows how participants (people, systems, components) interact **over time** by exchanging messages. Time flows **downwards**. It's the BA's best tool for specifying integrations and complex system interactions, and developers love it because it's precise.

### Elements

| Element | Notation | Meaning |
|---|---|---|
| **Participant / lifeline** | Box at top with a dashed line going down | An actor, system or component that takes part |
| **Actor** | Stick figure at top | A human user |
| **Synchronous message** | Solid line, filled arrowhead ──► | Sender waits for a reply |
| **Asynchronous message** | Solid line, open arrowhead ──> | Sender doesn't wait |
| **Return message** | Dashed line ◄┄┄ | Response to a message |
| **Activation bar** | Thin rectangle on a lifeline | Participant is busy processing |
| **Self-message** | Arrow looping back to the same lifeline | Internal processing |
| **Combined fragments** | Labelled box around messages | Logic: `alt` (if/else), `opt` (optional), `loop` (repeat), `par` (parallel) |

### Example: card payment

```
Customer        Shop Website        Payment Provider        Bank
   │                 │                     │                  │
   │ Pay £40 ───────►│                     │                  │
   │                 │ Authorise £40 ─────►│                  │
   │                 │                     │ Check funds ────►│
   │                 │                     │◄┄┄┄┄ Approved ┄┄┄│
   │                 │◄┄┄┄ Auth OK ┄┄┄┄┄┄┄┄│                  │
   │                 │─┐ Create order      │                  │
   │                 │◄┘                   │                  │
   │◄┄ Confirmation ┄│                     │                  │
   │                 │ Send email ──>  (Email service)        │
```

### Combined fragments

```
┌ alt ───────────────────────────────────────────┐
│ [funds available]                               │
│   Bank ┄┄ Approved ┄┄► Payment Provider         │
├─────────────────────────────────────────────────┤
│ [insufficient funds]                            │
│   Bank ┄┄ Declined ┄┄► Payment Provider         │
│   Payment Provider ┄┄ Declined ┄┄► Shop Website │
└─────────────────────────────────────────────────┘
```

| Fragment | Meaning | Example |
|---|---|---|
| `alt` | Alternatives: if / else | Approved vs declined |
| `opt` | Optional: happens only if condition true | Send SMS if the customer opted in |
| `loop` | Repeat | Retry 3 times on timeout |
| `par` | Parallel | Send email and update loyalty points at the same time |

### Why BAs use sequence diagrams

- Specify **interfaces**: what data goes where, in what order.
- Expose **error handling**: what if the provider doesn't respond?
- Clarify **responsibilities**: which system validates, which stores.
- Give developers and testers a precise, shared picture.

## Real-world examples

| Integration | What the sequence diagram exposed |
|---|---|
| Hotel booking ↔ channel manager | No message for cancellations had been specified |
| Mobile app login with SSO | Token refresh step was missing, so users would be logged out every hour |
| Retail POS ↔ loyalty system | Points were awarded before payment confirmed; reversed the order to avoid fraud |

## Step-by-step demonstration

**Scenario:** Model "Patient books appointment" across systems.

**Step 1: Identify participants.** Patient, Booking App, Booking System (back end), Patient Record System, SMS Gateway.

**Step 2: List the messages in order (happy path).**
1. Patient → App: select slot
2. App → Booking System: reserve slot (patient ID, slot ID)
3. Booking System → Patient Record System: verify patient
4. Patient Record System → Booking System: patient valid
5. Booking System: save appointment (self-message)
6. Booking System → App: booking confirmed (reference)
7. Booking System → SMS Gateway: send confirmation (asynchronous)
8. App → Patient: show confirmation

**Step 3: Add alternatives with `alt`.**
- `[slot already taken]` → Booking System returns "slot unavailable" → App shows alternatives.
- `[patient not found]` → Booking System returns error → App asks patient to contact clinic.

**Step 4: Add `opt` and `loop`.**
- `opt [patient opted in to SMS]` around message 7.
- `loop [up to 3 times, on timeout]` around messages 3-4.

**Step 5: Review with the architect.** They point out the slot should be held for 5 minutes while the patient confirms. Add a "hold slot" message and a "release hold" on timeout.

## Practical example

Turn this description into an ordered message list:

> *"When a user resets a password, the website asks the user service to create a reset token. The user service stores the token and asks the email service to send a link. The user clicks the link; the website checks the token with the user service; if valid, the user sets a new password."*

1. User → Website: request password reset (email)
2. Website → User Service: create reset token
3. User Service: store token (self)
4. User Service → Email Service: send reset link (async)
5. User → Website: open reset link (token)
6. Website → User Service: validate token
7. `alt [valid]` User Service ┄► Website: valid → User → Website: new password → Website → User Service: update password
   `[invalid or expired]` User Service ┄► Website: invalid → Website → User: show "link expired"

## Common mistakes

1. **Only the happy path.** Integrations fail; model errors, timeouts and retries.
2. **Too many participants.** Keep to the ones that matter for the question; split large flows.
3. **Unclear message names.** Use verbs with key data: "Authorise payment (amount, card token)".
4. **Mixing sync and async** without meaning to. Ask whether the sender waits.
5. **Designing the code.** Stay at the level of systems and key messages unless the team needs more.
