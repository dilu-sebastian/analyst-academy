## Explanation

### A common language for business processes

Flowcharts are great, but everyone draws them slightly differently. **BPMN (Business Process Model and Notation)** is an international standard (ISO/IEC 19510, maintained by the OMG) for drawing business processes so that **business people, analysts and developers all read them the same way**. Current version: **BPMN 2.0**.

| | Flowchart | BPMN |
|---|---|---|
| Notation | Informal, varies | Standardised |
| Events (timers, messages, errors) | Not really | Rich set of event types |
| Multiple organisations | Hard to show | Pools and message flows |
| Executable by software | No | Yes, in workflow engines (e.g. Camunda) |
| Learning curve | Very low | Low for basics, higher for the full set |

### The four element families

| Family | Shape | What it represents |
|---|---|---|
| **Flow objects** | Events ○, Activities ▭ (rounded), Gateways ◇ | The things that happen |
| **Connecting objects** | Sequence flow →, Message flow ┄○┄►, Association ┈ | How things connect |
| **Swimlanes** | Pools and lanes | Who does it |
| **Artefacts** | Data objects, groups, text annotations | Extra information |

### The basic shapes (90% of real diagrams)

```
 ○  Start event (thin circle)          ◉  End event (thick circle)
 ▢  Task (rounded rectangle)           ◇  Gateway (diamond): X exclusive, + parallel
 →  Sequence flow (within a pool)      ┄► Message flow (between pools)
 ┌──────────────┐
 │ Pool / Lane  │  who performs the steps
 └──────────────┘
```

### A first BPMN diagram (text sketch)

```
┌ Pizza Shop ──────────────────────────────────────────────────────────────┐
│ Counter │ ○ Order received → [Take payment] → ◇X paid? ─no→ [Cancel] → ◉ │

```

### Levels of BPMN use

| Level | Purpose | Who reads it |
|---|---|---|
| **Descriptive** | High-level overview, basic shapes only | Executives, business users |
| **Analytical** | Detailed, with event types, exceptions | BAs, process owners, analysts |
| **Executable** | Precise enough to run in a workflow engine | Developers, process automation teams |

Most BAs work at **descriptive and analytical** levels.

## Step-by-step demonstration

**Scenario:** Model a simple "leave request" process in descriptive BPMN.

**Step 1: Name the process and pool.** Pool: *Company*. Lanes: *Employee*, *Manager*, *HR System*.

**Step 2: Start event.** "Leave needed" in the Employee lane.

**Step 3: Tasks in order.**
- Employee: *Submit leave request*
- Manager: *Review request*
- Gateway (exclusive): *Approved?*
- Yes → HR System: *Update leave balance* → Employee: *Receive confirmation* → End "Leave booked"
- No → Employee: *Receive rejection* → End "Leave rejected"

**Step 4: Check the rules.**
- Every path from the start reaches an end ✓
- Task names are verb-noun ✓
- Gateway is a question with labelled exits ✓
- Sequence flows stay inside the pool ✓

**Step 5: Share with HR** and confirm. They add: *if the manager doesn't respond within 3 days, it escalates.* That needs a timer event, covered in the next lesson.

## Practical example

Translate these flowchart elements into BPMN:

| Flowchart element | BPMN element |
|---|---|
| Oval "Start" | Start event (thin circle) |
| Rectangle "Check stock" | Task (rounded rectangle) |
| Diamond "In stock?" | Exclusive gateway (diamond, optionally with X) |
| Oval "End" | End event (thick circle) |
| Swimlane "Warehouse" | Lane inside a pool |

## Common mistakes

1. **Using every BPMN symbol.** Start with the basic set; add advanced symbols only when needed.
2. **Sequence flows between pools.** Use message flows between separate organisations.
3. **Gateways that do work.** A gateway only routes; the decision work happens in the task before it.
4. **Missing end events.** Every path must end explicitly.
5. **Unnamed elements.** Label events, tasks and gateway paths.
