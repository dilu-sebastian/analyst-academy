## Explanation

### Events: things that happen

Events are circles. The **border** tells you *when*; the **icon** inside tells you *what kind*.

| Border | Position | Meaning |
|---|---|---|
| Thin single line ○ | **Start** | Triggers the process |
| Double line ◎ | **Intermediate** | Happens during the process |
| Thick line ◉ | **End** | Process (or path) finishes |

| Icon (trigger type) | Start example | Intermediate example | End example |
|---|---|---|---|
| **None** (empty) | Process starts manually | Milestone reached | Process ends |
| **Message** ✉ | Order received by email | Wait for supplier reply | Send confirmation |
| **Timer** ⏱ | Every Monday 9am | Wait 3 days | (not used) |
| **Error** ⚡ | (in sub-processes) | Catch payment failure | Throw error |
| **Signal** △ | Broadcast received | Price change announced | Broadcast sent |
| **Conditional** ≡ | Stock below 10 | Temperature above limit | (not used) |

**Boundary events** sit on the edge of a task and interrupt or branch from it, e.g. a timer on "Manager approves" that escalates after 3 days.

```
   [Manager approves]──⏱(3 days)──► [Escalate to director]
```

### Activities: work being done

| Type | Notation | Meaning |
|---|---|---|
| **Task** | Rounded rectangle | Atomic unit of work |
| **Sub-process** | Rounded rectangle with **+** | A group of tasks shown elsewhere (collapsed) or inside (expanded) |
| **Call activity** | Thick-bordered rounded rectangle | Reuses a globally defined process |

**Task types** (small icon in the corner):

| Icon | Task type | Example |
|---|---|---|
| 👤 | User task: a person with a system | Agent reviews claim in CRM |
| ✋ | Manual task: no system | Pack parcel |
| ⚙ | Service task: automated | System calculates tax |
| ✉ | Send / receive task | Send invoice |
| 📜 | Business rule task | Apply discount rules |
| 📝 | Script task | Run validation script |

**Markers:** ↻ loop (repeat), ||| parallel multi-instance (do for each item at once), ≡ sequential multi-instance.

### Gateways: controlling the flow

| Gateway | Symbol | Splitting behaviour | Merging behaviour |
|---|---|---|---|
| **Exclusive (XOR)** | ◇ or ◇ with X | Exactly **one** path, based on conditions | Passes through the first arriving flow |
| **Parallel (AND)** | ◇ with + | **All** paths at once | Waits for **all** incoming paths |
| **Inclusive (OR)** | ◇ with ○ | **One or more** paths, based on conditions | Waits for all **activated** paths |
| **Event-based** | ◇ with pentagon in circles | Path chosen by **which event happens first** | n/a |

```
Exclusive:   ◇X ─[≤ £500]→ [Auto-approve]
                └[> £500]→ [Manager approves]

Parallel:    ◇+ ──→ [Book flights]   ──→ ◇+
                └─→ [Book hotel]     ──┘     (wait for both)

Inclusive:   ◇○ ─[wants insurance]→ [Add insurance] ─→ ◇○
                └[wants car]→      [Add car hire]  ─┘   (one, both, or ...)

Event-based: ◇⬠ ─→ ✉ Customer replies  → [Process reply]
                 └→ ⏱ 7 days pass      → [Close case]
```

## Real-world examples

| Process | Elements used |
|---|---|
| Subscription renewal | Timer start event (30 days before expiry), service task sends reminder, event-based gateway: customer pays vs 30 days pass |
| Insurance claim | Exclusive gateway on claim value, boundary timer to escalate, error event if fraud detected |
| Employee onboarding | Parallel gateway: IT setup, HR paperwork and building pass in parallel |
| Travel booking | Inclusive gateway for optional extras |

## Step-by-step demonstration

**Scenario:** Improve the leave request model from the previous lesson with HR's new rule: *if the manager doesn't respond in 3 days, escalate to the department head.*

**Step 1: Start event.** None start: "Leave needed".

**Step 2: User task.** Employee: *Submit leave request* (👤).

**Step 3: Service task.** System: *Check leave balance* (⚙).

**Step 4: Exclusive gateway.** *Enough balance?* No → *Notify employee: insufficient balance* → End. Yes → continue.

**Step 5: User task with boundary timer.** Manager: *Review request* with a boundary timer of 3 days → Department head: *Review request*.

**Step 6: Exclusive gateway.** *Approved?* Yes → System: *Update balance* (⚙) → *Send confirmation* (✉ send task) → End "Leave booked". No → *Send rejection* → End "Leave rejected".

**Step 7: Check.** Each gateway has labelled conditions that cover all cases; every path ends; task types match reality.

## Practical example

Pick the right gateway:

| Situation | Gateway |
|---|---|
| Route an order to standard or express shipping based on customer choice | Exclusive |
| After a hire is approved, IT, HR and Facilities all start preparing | Parallel |
| A patient may need blood tests, X-ray, both or neither based on symptoms | Inclusive |
| Wait for either the customer's documents or a 14-day deadline | Event-based |

## Common mistakes

1. **Using an exclusive gateway to merge parallel paths.** Parallel splits need a parallel join, or the flow continues too early.
2. **Unlabelled gateway conditions.** Every outgoing flow from an exclusive or inclusive gateway needs a condition.
3. **Timer start used for waiting mid-process.** Waiting is an intermediate timer event.
4. **Overusing task type icons.** Use them when the distinction matters (manual vs automated).
5. **Gateways named as actions.** "Approve invoice" is a task; the gateway asks "Approved?".
