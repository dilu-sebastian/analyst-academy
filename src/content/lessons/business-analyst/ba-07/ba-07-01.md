> **Prerequisites:** ba-02 Business Requirements

## Explanation

### Requirements told from the user's point of view

A **user story** is a short, simple description of a feature written from the perspective of the person who wants it. It's the main way requirements are expressed in Agile teams.

The standard template:

```
As a  <type of user>
I want  <some goal or capability>
So that  <some benefit or reason>
```

Example:
> **As a** frequent shopper, **I want** to reorder a previous basket in one click **so that** I save time on my weekly shop.

| Part | Purpose | Tip |
|---|---|---|
| **As a** (who) | The user role who benefits | Be specific: "first-time buyer", not "user" |
| **I want** (what) | The capability or goal | Describe the goal, not the UI |
| **So that** (why) | The value or benefit | Never skip it: it guides design and priority |

### A story is a promise of a conversation

User stories are deliberately short. They are not complete specifications. Ron Jeffries described stories with the **3 Cs**:

| C | Meaning |
|---|---|
| **Card** | The story is written on a card (or Jira ticket): short enough to fit |
| **Conversation** | Details emerge through discussion between the BA/PO, developers, testers and users |
| **Confirmation** | Acceptance criteria confirm when the story is done |

### Stories vs traditional requirements

| Traditional requirement | User story |
|---|---|
| "The system shall allow users to reset passwords via email." | "As a registered customer, I want to reset my password by email so that I can regain access without calling support." |
| System-centred | User-centred |
| Often complete spec up front | Detail added just in time |
| "Shall" language | Conversational |
| Value often implicit | Value explicit ("so that") |

### Where stories sit: epics, features, stories, tasks

```
Theme / Initiative:  Improve self-service
  └─ Epic:           Account management
       ├─ Feature:   Password management
       │    ├─ Story: Reset password by email
       │    └─ Story: Change password when logged in
       └─ Feature:   Profile
            └─ Story: Update delivery address
                  └─ Tasks: build API, update UI, write tests (developer tasks)
```

| Level | Size | Example |
|---|---|---|
| **Epic** | Too big for one sprint; weeks or months | Online returns |
| **Feature** | A group of related stories | Return label generation |
| **Story** | Fits in one sprint (usually a few days) | Print a prepaid return label |
| **Task** | Hours; technical work to deliver a story | Create PDF template |

### Who writes stories?

Anyone can, but usually the **Product Owner** owns the backlog and the **BA** helps write, refine and add detail. The best stories are written **with** users and the team.

## Real-world examples

| Product | User story |
|---|---|
| Banking app | As a customer travelling abroad, I want to freeze my card instantly so that I'm protected if it's lost. |
| Hospital system | As a ward nurse, I want to see which patients are due medication in the next hour so that no doses are missed. |
| Online course | As a learner, I want to resume a video where I left off so that I don't waste time searching. |
| HR portal | As a line manager, I want to approve leave from my phone so that requests aren't delayed when I'm travelling. |

## Step-by-step demonstration

**Scenario:** Turn the requirement *"BR-03: Members shall join a waitlist for full classes"* into stories.

**Step 1: Identify users.** Member, instructor, gym manager.

**Step 2: Ask each user what they want and why.**
- Member wants to get a place in a full class.
- Instructor wants to know how many are waiting (to request a bigger room).
- Manager wants to see demand to plan more classes.

**Step 3: Write stories.**
1. *As a member, I want to join the waitlist for a full class so that I can still get a place if someone cancels.*
2. *As a member on a waitlist, I want to be notified when a place becomes available so that I can claim it quickly.*
3. *As an instructor, I want to see how many members are waiting for my class so that I can request a larger room.*
4. *As a gym manager, I want a weekly report of waitlist numbers by class so that I can schedule extra sessions where demand is high.*

**Step 4: Check the "so that".** Each has a clear benefit that helps the team prioritise. Story 4 might be lower priority; stories 1 and 2 deliver the core value.

**Step 5: Plan the conversation.** Questions for refinement: *How long does a member have to accept? Max waitlists per member? What if the class starts in 1 hour?* These answers become acceptance criteria.

## Practical example

Improve these stories:

| Weak | Problem | Better |
|---|---|---|
| As a user, I want a button. | Vague user; UI not goal; no value | As a returning customer, I want to save my card details so that checkout is faster next time. |
| As a developer, I want to refactor the database. | Not user value (technical task) | Treat as a technical task or enabler linked to a user story, or phrase the value: "As an operations manager, I want order searches to return in under 2 s so that..." |
| As an admin, I want to manage users. | Too big (epic) | Split: create user, deactivate user, reset a user's password, assign roles |
| I want to filter products by price. | Missing who and why | As a budget-conscious shopper, I want to filter products by price so that I only see items I can afford. |

## Common mistakes

1. **Skipping "so that".** Without the why, the team can't make smart trade-offs.
2. **Generic "As a user".** Specific roles reveal different needs.
3. **Writing UI instructions.** "I want a dropdown" limits design; describe the goal.
4. **Stories too big.** If it can't be finished in a sprint, it's an epic; split it.
5. **Treating the card as the full specification.** Conversation and acceptance criteria are essential.
