> **Prerequisites:** ba-07-01 What is a user story?

## Explanation

### A quality checklist for stories

Bill Wake's **INVEST** acronym lists six qualities of a good user story. Use it to review every story before it enters a sprint.

| Letter | Quality | Meaning | Question to ask |
|---|---|---|---|
| **I** | Independent | Can be built and delivered without depending on other stories in the same sprint | *Can we deliver this on its own, in any order?* |
| **N** | Negotiable | Details are open to discussion; it's not a contract | *Is there room to discuss how we meet the need?* |
| **V** | Valuable | Delivers value to a user or the business | *Who benefits, and would they notice?* |
| **E** | Estimable | The team understands it well enough to estimate | *Can the team size it?* |
| **S** | Small | Fits comfortably in one sprint (ideally a few days) | *Can we finish it in a sprint?* |
| **T** | Testable | Clear acceptance criteria can confirm it's done | *How will we know it works?* |

### Each letter in practice

**Independent.** Dependencies create scheduling headaches. Combine tightly coupled stories, or split differently.
- ✗ "Add card payment" and "Show payment confirmation" are tightly linked.
- ✓ "Pay by card and see confirmation" as one thin slice.

**Negotiable.** The story states the need; the team decides how.
- ✗ "As a user, I want a red pop-up modal with a 5-second timer..."
- ✓ "As a user, I want to be warned before my session expires so that I don't lose my work."

**Valuable.** Avoid purely technical stories with no visible value; slice **vertically**.

```
 Horizontal slicing (bad)           Vertical slicing (good)
 ┌──────────── UI ────────────┐     ┌──┐ ┌──┐ ┌──┐
 ├──────── Business logic ────┤     │UI│ │UI│ │UI│
 ├──────── Database ──────────┤     │BL│ │BL│ │BL│
 └────────────────────────────┘     │DB│ │DB│ │DB│
 "Build the DB layer" has no         └──┘ └──┘ └──┘
 user value on its own               each slice works end to end
```

**Estimable.** If the team can't estimate, something is missing: unclear scope, unknown technology, or missing domain knowledge. Resolve with conversation, or a **spike** (a short time-boxed investigation).

**Small.** Big stories hide risk. Rule of thumb: a story should take no more than half a sprint; many teams aim for 1-3 days.

**Testable.** "Easy to use" isn't testable; "a first-time user can complete checkout in under 3 minutes" is.

### INVEST is a guide, not a law

Perfect independence is often impossible. Use INVEST to spot problems and improve stories, not to reject everything.

## Real-world examples

| Original story | INVEST problem | Fix |
|---|---|---|
| As a shopper, I want the whole checkout redesigned | Not Small, not Estimable | Split into address entry, delivery options, payment, confirmation |
| As a developer, I want to set up the database | Not Valuable (horizontal) | Make part of the first vertical slice, e.g. "save a customer's address" |
| As a user, I want the app to be fast | Not Testable | "Search results appear within 2 seconds for 95% of searches" |
| As a customer, I want a blue Submit button bottom right | Not Negotiable | "As a customer, I want to submit my order easily so that..." |

## Step-by-step demonstration

**Scenario:** Review this story with INVEST:
> *"As a member, I want to manage my bookings."*

**I – Independent?** Unclear; "manage" might include features depending on payments. ⚠
**N – Negotiable?** Yes.
**V – Valuable?** Yes, but vague.
**E – Estimable?** No: "manage" could mean anything. ✗
**S – Small?** No: likely view, cancel, reschedule, history. ✗
**T – Testable?** No clear criteria. ✗

**Rewrite by splitting:**
1. *As a member, I want to see my upcoming bookings so that I know when my next classes are.*
2. *As a member, I want to cancel a booking so that my place goes to someone else.*
3. *As a member, I want to move a booking to another session of the same class so that I don't lose my place when my plans change.*
4. *As a member, I want to see my past attendance so that I can track my progress.*

**Re-check story 2:** Independent ✓, Negotiable ✓, Valuable ✓ (member and gym), Estimable ✓, Small ✓ (1-2 days), Testable ✓ (e.g. *cancelled up to 2 hours before; place released to waitlist*).

## Practical example

Score each story against INVEST and note the main issue:

| Story | Main issue |
|---|---|
| As an admin, I want the system to be secure | Not testable; too broad |
| As a customer, I want to log in with Google so that I don't need another password | Good, assuming the team can estimate the Google integration (maybe a spike first) |
| Create the orders table | Not valuable on its own; horizontal slice |
| As a buyer, I want to track my order on a live map, get SMS updates, rate my courier and tip them | Not small; split into 4 stories |

## Common mistakes

1. **Treating INVEST as a gate that blocks all stories.** Use it to improve, not to reject.
2. **Horizontal slicing.** Building by layer delays value and feedback.
3. **Ignoring dependencies.** Spot them early and order the backlog accordingly.
4. **Stories that dictate UI.** Keep stories negotiable; agree design with the team.
5. **Missing acceptance criteria.** Without them, a story fails the T.
