## Explanation

### How do we know the story is done?

**Acceptance criteria (AC)** are the conditions a story must satisfy to be accepted by the Product Owner. They turn a short story into something the team can build and test, and they're the third C of the 3 Cs: **Confirmation**.

> **Story:** As a registered customer, I want to reset my password by email so that I can regain access without calling support.
>
> **Acceptance criteria:**
> 1. A "Forgot password" link is available on the login page.
> 2. Entering a registered email sends a reset link within 2 minutes.
> 3. Entering an unregistered email shows the same message (for security, don't reveal if the email exists).
> 4. The reset link expires after 30 minutes and can be used once.
> 5. The new password must meet the password policy (min 12 characters).
> 6. After resetting, the customer is logged in and receives a confirmation email.

### What good acceptance criteria do

| Purpose | Why it matters |
|---|---|
| Define scope | Shows what's included (and by omission, what isn't) |
| Shared understanding | Developers, testers and PO agree before work starts |
| Basis for testing | Each criterion becomes one or more test cases |
| Definition of "done" for this story | No arguing at the sprint review |
| Enable estimation | The team sizes the work more accurately |

### Formats

| Format | Example | Best for |
|---|---|---|
| **Rule-based (checklist)** | "Reset link expires after 30 minutes" | Most stories; simple rules |
| **Scenario-based (Given-When-Then)** | "Given an expired link, When the customer opens it, Then show 'link expired'" | Behaviour with different situations; automation (ba-07-04) |

### What to cover

Use this checklist to make sure criteria are complete:

| Area | Example question |
|---|---|
| **Happy path** | What happens when everything goes right? |
| **Business rules** | Limits, calculations, conditions? |
| **Validation** | Required fields, formats, ranges? |
| **Errors / edge cases** | What if input is wrong, empty, duplicate? |
| **Permissions** | Who can and can't do it? |
| **Notifications** | Who is told, how, when? |
| **Non-functional** | Response time, accessibility, security for this story? |

### Acceptance criteria vs Definition of Done

| Acceptance criteria | Definition of Done (DoD) |
|---|---|
| Specific to **one** story | Applies to **every** story |
| Functional behaviour | Quality standards |
| "Reset link expires after 30 min" | "Code reviewed, unit tests pass, deployed to test, docs updated" |
| Written by PO/BA with team | Agreed by the whole team |

A story is complete when it meets **both** its acceptance criteria and the DoD.

### Writing tips

- Write from the user's perspective, in plain language.
- Each criterion should be **testable**: pass or fail.
- Describe **what**, not **how** (avoid UI micro-details unless they matter).
- Typically **3-8 criteria** per story. More than 10 suggests the story should be split.
- Write them **before** development starts, ideally in refinement with developers and testers.

## Real-world examples

**Story:** As a shopper, I want to apply a discount code at checkout so that I pay the promotional price.

| # | Acceptance criterion |
|---|---|
| 1 | A discount code field appears on the checkout page |
| 2 | A valid code reduces the order total by the code's value before delivery charges |
| 3 | An expired code shows "This code has expired" and the total is unchanged |
| 4 | An invalid code shows "Code not recognised" |
| 5 | Only one code can be applied per order |
| 6 | Codes are not case-sensitive |
| 7 | The discount appears as a separate line on the order confirmation and email |

## Step-by-step demonstration

**Story:** *As a member, I want to cancel a class booking so that my place goes to someone else.*

**Step 1: Happy path.** *Member can cancel an upcoming booking from "My bookings"; booking status shows Cancelled.*

**Step 2: Business rules.** Ask the PO: cancellation cut-off? → *Up to 2 hours before start without penalty; later cancellations count as a no-show.*

**Step 3: Side effects.** What happens to the place? → *Offered to the first person on the waitlist.*

**Step 4: Errors and edge cases.** Class already started? → *Cannot cancel.* Double-click? → *Only one cancellation processed.*

**Step 5: Notifications.** → *Member receives cancellation confirmation email.*

**Step 6: Write the AC.**
1. A member can cancel any upcoming booking from "My bookings".
2. Cancelling more than 2 hours before the class start time records the booking as Cancelled with no penalty.
3. Cancelling within 2 hours of the start records it as Late cancellation and counts towards the no-show limit; the member sees a warning before confirming.
4. Bookings for classes that have already started cannot be cancelled.
5. When a booking is cancelled, the place is offered to the first member on the waitlist.
6. The member receives a cancellation confirmation email within 5 minutes.

**Step 7: Review with the team.** The tester asks: *What if the class itself was cancelled by the gym?* → Out of scope for this story; separate story created.

## Practical example

Improve these acceptance criteria:

| Weak | Problem | Better |
|---|---|---|
| The page should load fast | Not testable | The bookings page loads within 2 s for 95% of requests |
| Handle errors properly | Vague | If payment is declined, show "Payment declined, please try another card" and keep the basket |
| Use a green tick icon on success | Design detail | A success message confirms the booking with the class name, date and time |
| Works like the old system | Undefined | List the specific behaviours |

## Common mistakes

1. **Writing AC after development.** They must guide the build, not describe it afterwards.
2. **Only the happy path.** Most defects hide in error and edge cases.
3. **Vague criteria.** "Properly", "fast", "user-friendly" can't be tested.
4. **Too many criteria.** More than ~10 means the story is too big.
5. **Confusing AC with the DoD.** AC are story-specific; the DoD applies to all stories.
