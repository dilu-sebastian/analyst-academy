## Explanation

### Acceptance criteria as scenarios

**Given-When-Then** is a structured way to write acceptance criteria as concrete scenarios. It comes from **Behaviour-Driven Development (BDD)**, and the formal syntax is called **Gherkin**.

```
Given  <a starting context / precondition>
When   <an action or event happens>
Then   <an expected outcome>
```

| Keyword | Purpose | Example |
|---|---|---|
| **Given** | Set the scene: state of the system and user | Given I am a logged-in member with 2 future bookings |
| **When** | The action or trigger | When I cancel the booking for Monday's yoga class |
| **Then** | The observable result | Then the booking shows as Cancelled |
| **And / But** | Add more conditions or outcomes | And I receive a cancellation email |

### Gherkin syntax

```gherkin
Feature: Discount codes
  As a shopper
  I want to apply discount codes at checkout
  So that I pay the promotional price

  Background:
    Given I have items worth £80 in my basket
    And I am on the checkout page

  Scenario: Valid code reduces the total
    When I apply the code "SAVE10"
    Then the order total is £72.00
    And the discount line shows "SAVE10 -£8.00"

  Scenario: Expired code is rejected
    Given the code "SUMMER" expired yesterday
    When I apply the code "SUMMER"
    Then I see the message "This code has expired"
    And the order total is £80.00
```

| Gherkin keyword | Meaning |
|---|---|
| `Feature` | The capability, often with the user story text |
| `Background` | Steps common to every scenario in the feature |
| `Scenario` | One concrete example |
| `Scenario Outline` + `Examples` | One template run with many data rows |
| `Given / When / Then / And / But` | Steps |

### Scenario Outline: many examples, one template

```gherkin
Scenario Outline: Delivery charge depends on order value
  Given my basket total is <total>
  When I go to checkout
  Then the delivery charge is <delivery>

  Examples:
    | total  | delivery |
    | £20.00 | £3.99    |
    | £49.99 | £3.99    |
    | £50.00 | £0.00    |
    | £120   | £0.00    |
```

Boundary values (£49.99 and £50.00) make the rule unambiguous.

### Why teams use Gherkin

| Benefit | Explanation |
|---|---|
| **Shared language** | Business, developers and testers read the same scenarios |
| **Concrete examples** | Examples expose misunderstandings better than abstract rules |
| **Living documentation** | Scenarios describe how the system actually behaves |
| **Automation** | Tools like Cucumber, SpecFlow and Behave can run Gherkin as automated tests |

### The Three Amigos

BDD scenarios are best written in a short session with three perspectives:

| Amigo | Brings |
|---|---|
| **Business (PO/BA)** | What problem we're solving, the rules |
| **Development** | How it might work, technical constraints |
| **Testing** | What could go wrong, edge cases |

### Writing good scenarios

- **One behaviour per scenario.** If you need many Whens, split it.
- **Declarative, not imperative.** Describe behaviour, not clicks.

| Imperative (avoid) | Declarative (prefer) |
|---|---|
| Given I go to the login page And I type "sam@x.com" into the email box And I type "pw" And I click Login | Given I am logged in as a customer |

- **Use concrete data.** "£80" and "SAVE10" beat "some amount" and "a code".
- **Then describes observable outcomes**, not internal database states (unless that's what matters).

## Real-world examples

```gherkin
Feature: Card freeze (banking app)

  Scenario: Customer freezes a lost card
    Given I have an active debit card ending 4321
    When I freeze the card in the app
    Then card 4321 shows as Frozen
    And card payments with card 4321 are declined
    And I can unfreeze the card at any time

  Scenario: Direct debits continue on a frozen card
    Given card 4321 is frozen
    When my monthly gym direct debit is collected
    Then the direct debit is paid from my account
```

The second scenario captured a rule the business assumed but nobody had written down.

## Step-by-step demonstration

**Story:** *As a member, I want to join the waitlist for a full class so that I can still get a place if someone cancels.*

**Step 1: Three Amigos list examples.**
- Member joins a full class waitlist (happy path).
- Member tries to join a class that has space (should book instead).
- Member already on 3 waitlists (limit).
- A place frees up; first person is offered it.
- Offer not accepted in 2 hours; goes to next person.

**Step 2: Write scenarios.**

```gherkin
Feature: Class waitlist

  Background:
    Given I am a logged-in member

  Scenario: Join the waitlist for a full class
    Given the Tuesday 18:00 Spin class is full
    And there are 2 members on its waitlist
    When I join the waitlist
    Then I am number 3 on the waitlist
    And I receive an email confirming my position

  Scenario: Cannot join more than 3 waitlists
    Given I am already on 3 waitlists
    When I try to join the waitlist for Thursday Yoga
    Then I see "You can be on up to 3 waitlists at a time"

  Scenario: First on the waitlist is offered a freed place
    Given I am number 1 on the waitlist for Tuesday Spin
    When a booked member cancels
    Then I am offered the place by email and SMS
    And I have 2 hours to accept

  Scenario: Unaccepted offer passes to the next member
    Given I was offered a place 2 hours ago
    And I have not accepted
    When the offer expires
    Then the place is offered to number 2 on the waitlist
```

**Step 3: Review.** Developer asks: *What if the class starts in under 2 hours?* → add a scenario for auto-booking.

## Practical example

Rewrite in Given-When-Then:

> *"If a user enters the wrong password 5 times, the account is locked for 15 minutes."*

```gherkin
Scenario: Account locks after 5 failed attempts
  Given I have entered a wrong password 4 times
  When I enter a wrong password again
  Then my account is locked for 15 minutes
  And I see "Too many attempts. Try again in 15 minutes."

Scenario: Account unlocks after 15 minutes
  Given my account was locked 15 minutes ago
  When I log in with the correct password
  Then I am logged in successfully
```

## Common mistakes

1. **Imperative, click-by-click steps.** They're brittle and hard to read.
2. **Several behaviours in one scenario.** Hard to understand and to diagnose failures.
3. **Vague data.** "Some items" makes outcomes untestable; use real values.
4. **Writing scenarios alone.** Three Amigos catch far more gaps.
5. **Gherkin for everything.** Simple rules may be clearer as a checklist.
