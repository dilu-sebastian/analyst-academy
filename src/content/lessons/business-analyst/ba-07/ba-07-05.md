## Explanation

### Big stories are risky

Large stories are hard to estimate, hard to finish in a sprint, and delay feedback. **Story splitting** breaks big stories (or epics) into smaller ones that **each still deliver value**. **Backlog refinement** is the ongoing activity where the team does this, along with clarifying and estimating.

### Common splitting patterns

These patterns (popularised by Richard Lawrence and others) cover most situations:

| Pattern | Split by... | Example epic → stories |
|---|---|---|
| **Workflow steps** | Steps in a process | "Online returns" → request return; print label; track return; receive refund |
| **Business rule variations** | Different rules | "Calculate shipping" → flat rate; free over £50; express surcharge |
| **Happy path vs exceptions** | Main flow first, errors later | "Pay by card" → successful payment; declined card; 3D Secure challenge |
| **Simple / complex** | Basic version first | "Search products" → search by name; add filters; add spell-correction |
| **Data variations** | Types of data | "Import contacts" → from CSV; from Gmail; from Outlook |
| **Interface / platform** | Channel or device | "Book appointment" → web; iOS; Android |
| **User roles** | Who uses it | "Manage bookings" → member; receptionist; manager |
| **Operations (CRUD)** | Create, read, update, delete | "Manage addresses" → add; view; edit; delete |
| **Defer performance** | Make it work, then fast | "Report generation" → generate report; generate in under 5 s |
| **Spike** | Learn first | "Integrate with new courier" → 1-day spike; then build |

### Rules for a good split

1. Each new story is **valuable** on its own (vertical slice).
2. Each is **small** enough for a sprint.
3. Splits should let the PO **prioritise**: some parts may be Won't-have.
4. Avoid splitting by technical layer (UI / API / database).

### The SPIDR shortcut

Mike Cohn's **SPIDR**: split by **S**pikes, **P**aths, **I**nterfaces, **D**ata, **R**ules.

### Backlog refinement

**Refinement** (formerly "grooming") is an ongoing activity where the PO, BA and team prepare backlog items for upcoming sprints.

| Activity | Purpose |
|---|---|
| **Clarify** | Discuss stories, answer questions, add details |
| **Split** | Break large items into sprint-sized stories |
| **Write acceptance criteria** | Define confirmation conditions |
| **Estimate** | Size items (story points, T-shirt sizes) |
| **Order** | Re-prioritise based on value, risk and dependencies |
| **Remove** | Delete items no longer needed |

**Guidelines:**
- Many teams spend up to about **10% of sprint capacity** on refinement.
- Keep the top of the backlog "ready" for **1-2 sprints** ahead; lower items can stay rough.

```
  Product backlog (shaped like an iceberg / DEEP)
  ┌───────────────┐  top: small, detailed, estimated, ready
  │ ■ ■ ■ ■ ■      │
  │  ■■   ■■   ■■  │  middle: medium stories, rough estimates
  │   ████   ████  │  bottom: epics, ideas, little detail
  └───────────────┘
```

**DEEP** backlog (Roman Pichler): **D**etailed appropriately, **E**stimated, **E**mergent (changes over time), **P**rioritised.

### Definition of Ready

Many teams agree a **Definition of Ready (DoR)**: criteria a story must meet before entering a sprint, e.g.:
- Written in user story format with a clear value
- Acceptance criteria agreed
- Estimated by the team
- Dependencies identified
- Small enough for the sprint
- UX designs attached if needed

## Real-world examples

| Epic | Split used | First story delivered |
|---|---|---|
| Mobile banking: international payments | Simple/complex + rules | Send money to an EU account in EUR (other currencies later) |
| HR system: performance reviews | Workflow steps | Employee completes self-assessment |
| E-commerce: subscriptions | Happy path first | Customer subscribes monthly with card (pause, skip, cancel later) |

## Step-by-step demonstration

**Epic:** *As a shopper, I want to return items online so that I don't have to visit a store.*

**Step 1: Map the workflow.** Request return → choose reason → get label → send item → warehouse receives → refund issued → customer notified.

**Step 2: Split by workflow steps.**
1. Request a return for an order item, choosing a reason.
2. Download a prepaid return label.
3. See return status (requested, in transit, received, refunded).
4. Receive a refund to the original payment method once the warehouse confirms receipt.

**Step 3: Split further by rules / happy path.**
- Story 1a: Return a single item within 30 days (happy path).
- Story 1b: Block returns for non-returnable items (e.g. underwear, personalised).
- Story 1c: Return multiple items in one request.

**Step 4: Prioritise with the PO.** First release (MVP): 1a, 2, 4. Later: 1b, 1c, 3.

**Step 5: Write AC and estimate** in refinement for the top stories.

**Step 6: Check INVEST.** Each is independent enough, valuable, small and testable.

## Practical example

Split each epic using a suitable pattern:

| Epic | Pattern | Stories |
|---|---|---|
| Users can pay by card, PayPal and Apple Pay | Data variations / interfaces | Pay by card; pay by PayPal; pay by Apple Pay |
| Managers can view, export and schedule sales reports | Operations | View report; export to Excel; schedule weekly email |
| Search for flights with filters, sorting and flexible dates | Simple/complex | Basic search; filters; sorting; flexible dates |
| Members can book classes on web and mobile | Interface | Book on web; book on mobile app |

## Common mistakes

1. **Splitting by technical layer.** "Build API" and "Build UI" aren't valuable alone.
2. **Splitting so small that value disappears.** "Add a label to a field" is a task, not a story.
3. **Refining too far ahead.** Detailed stories for 6 months out will change; refine just in time.
4. **Refinement without the team.** The PO and BA alone miss technical insights and estimates.
5. **No Definition of Ready.** Unready stories cause sprints to stall.
