## Explanation

### Not a document factory

In an Agile team, the BA's value comes from **continuous analysis and collaboration**, not from handing over large documents. The BA helps the team build **the right thing**, while developers focus on building it **right**.

### What an Agile BA does

| Area | Activities |
|---|---|
| **Discovery** | Understand the problem, users and goals; run interviews, workshops, data analysis |
| **Backlog** | Write and refine epics, stories and acceptance criteria with the PO |
| **Modelling** | Process maps, story maps, journey maps, data models, just enough to clarify |
| **Collaboration** | Three Amigos, refinement facilitation, answering developer questions daily |
| **Quality** | Help testers with scenarios, review increments against needs, support UAT |
| **Stakeholders** | Keep stakeholders engaged, gather feedback at reviews, manage expectations |
| **Value** | Track outcomes, measure whether features deliver the expected benefit |

### Working one or two sprints ahead

The BA usually works **ahead of the developers**, preparing stories for upcoming sprints while supporting the current one.

```
          Sprint N            Sprint N+1          Sprint N+2
BA:  [support build of N]  [refine N+1 stories] [discover N+2 ideas]
Dev:      [build N]           [build N+1]         [build N+2]
```

This is sometimes called **dual-track Agile**: a **discovery track** (what should we build?) and a **delivery track** (build it).

### Story mapping

A **user story map** (Jeff Patton) arranges stories by user activity (left to right) and priority (top to bottom). It shows the whole journey and helps slice releases.

```
Activities:   Find class   │  Book class  │  Attend   │  Manage booking
─────────────────────────────────────────────────────────────────────────
Release 1:    View         │  Book a      │  See      │  Cancel
(MVP)         timetable    │  class       │  booking  │  booking
─────────────────────────────────────────────────────────────────────────
Release 2:    Filter by    │  Join        │  Check in │  Reschedule
              type/time    │  waitlist    │  by QR    │
─────────────────────────────────────────────────────────────────────────
Release 3:    Favourite    │  Book for a  │  Rate     │  Booking
              instructors  │  friend      │  class    │  history
```

### Skills that matter most in Agile

- **Facilitation**: short, focused sessions with the right people
- **Slicing**: breaking work into valuable thin slices
- **Writing**: clear, concise stories and AC
- **Collaboration**: daily informal conversations
- **Comfort with change**: requirements evolve; that's expected
- **Outcome thinking**: success = value delivered, not features shipped

### Measuring value: outputs vs outcomes

| Output (what we built) | Outcome (what changed) |
|---|---|
| Online booking released | 65% of bookings now online |
| Waitlist feature live | Empty spaces in popular classes down 40% |
| New FAQ page | Calls to reception down 25% |

The Agile BA helps define and track **outcomes**, so the PO can decide what to do next.

## Real-world examples

| Team | How the BA added value |
|---|---|
| Insurance quote app | BA used a story map to cut the MVP from 40 stories to 12; launched 3 months earlier |
| Utility company | BA ran Three Amigos for every story; defects found in testing dropped by 60% |
| Healthcare portal | BA tracked outcome data after each release; one feature with low uptake was simplified rather than extended |

## Step-by-step demonstration

**Scenario:** A typical sprint week for a BA on the gym booking team.

| Day | Activity |
|---|---|
| **Mon** | Sprint Planning: explain stories. Afternoon: interview 3 members about class preferences (discovery for future sprints). |
| **Tue** | Daily Scrum. Answer developer question on waitlist rules. Three Amigos for "Check in by QR code". |
| **Wed** | Daily Scrum. Update story map with interview insights. Draft stories for "Filter by class type". |
| **Thu** | Daily Scrum. Backlog refinement: split "Reschedule booking" into 2 stories; agree AC. Review analytics: booking drop-off at login step. |
| **Fri** | Daily Scrum. Test completed stories against AC with the tester. Prepare demo scenarios for next week's review. |

Notice the balance: **current sprint support**, **next sprint refinement**, and **future discovery**.

## Practical example

A developer messages: *"The story says members can cancel up to 2 hours before. What about classes that start at 6am? Members are asleep at 4am."*

Good BA response:
1. Acknowledge the insight: it's a real edge case.
2. Check with the PO quickly: *Is the 2-hour rule fixed?*
3. PO decides: for classes before 8am, the cut-off is 9pm the previous evening.
4. Update the acceptance criteria and add a scenario.
5. Tell the developer and tester; note the decision on the story.

Time taken: 20 minutes, no document revisions, no meeting needed.

## Common mistakes

1. **Writing everything up front.** Recreates Waterfall inside sprints.
2. **Being a proxy between team and users.** Bring developers to user sessions when possible.
3. **Only focusing on the current sprint.** Without discovery, the backlog runs dry.
4. **Measuring success by stories delivered.** Track outcomes instead.
5. **Unclear split with the PO.** Agree who decides and who analyses.
