## Explanation

### What is Jira?

**Jira** (by Atlassian) is the most widely used tool for planning and tracking work in Agile teams. BAs use it daily to write stories, manage the backlog, track progress and link requirements to delivery. Knowing Jira is listed in a large share of BA job adverts.

> Note: menus and names change between Jira versions (Cloud vs Data Center, team-managed vs company-managed projects). The concepts in this lesson are stable even when the buttons move.

### Core building blocks

| Concept | What it is | Example |
|---|---|---|
| **Site / instance** | Your organisation's Jira | `yourcompany.atlassian.net` |
| **Project** | A container for related work, usually one product or team | "Gym Booking (GYM)" |
| **Project key** | Short prefix for all issue IDs | `GYM` → GYM-42 |
| **Issue (work item)** | A single piece of work | A story, bug or task |
| **Issue type** | The kind of issue | Epic, Story, Task, Bug, Sub-task |
| **Field** | A piece of data on an issue | Summary, Description, Assignee, Priority, Story points |
| **Workflow** | The statuses an issue moves through | To Do → In Progress → In Review → Done |
| **Board** | Visual view of issues by status | Scrum board or Kanban board |
| **Filter / JQL** | Saved search | All open bugs in GYM |

### Issue type hierarchy

```
Epic          GYM-1   Online class booking
 ├─ Story     GYM-12  Book a class
 │   ├─ Sub-task GYM-13  Build booking API
 │   └─ Sub-task GYM-14  Booking confirmation email
 ├─ Story     GYM-15  Cancel a booking
 └─ Bug       GYM-30  Cancel button not shown on mobile
```

| Issue type | Use for |
|---|---|
| **Epic** | Large body of work spanning sprints |
| **Story** | User-facing functionality (As a ... I want ... so that) |
| **Task** | Work that isn't a user story (e.g. set up test environment) |
| **Bug** | Something that doesn't work as intended |
| **Sub-task** | A piece of a story or task, usually for developers |

### Anatomy of a well-written story in Jira

| Field | Example content |
|---|---|
| **Summary** | Member can cancel a class booking |
| **Description** | *As a member, I want to cancel a class booking so that my place goes to someone else.* + context, links to process map |
| **Acceptance criteria** (custom field or in description) | Numbered AC or Gherkin scenarios |
| **Epic / Parent** | GYM-1 Online class booking |
| **Priority** | High |
| **Story points** | 3 |
| **Labels / Components** | `bookings`, `mobile` |
| **Attachments / links** | Wireframe, Confluence requirements page |
| **Linked issues** | *blocks* GYM-20, *relates to* GYM-8 |

### Workflows

A **workflow** defines statuses and allowed transitions.

```
 To Do ──► In Progress ──► In Review ──► In Test ──► Done
   ▲            │                            │
   └────────────┴──────── (reopen) ◄─────────┘
```

Teams customise workflows; BAs often help define statuses like *Ready for Dev* or *In UAT* and the rules for moving between them.

### Searching with JQL

**JQL (Jira Query Language)** lets you build precise searches. Useful BA queries:

```sql
project = GYM AND type = Story AND status = "To Do" ORDER BY rank
project = GYM AND "Epic Link" = GYM-1          -- (older Jira; newer uses parent = GYM-1)
project = GYM AND type = Bug AND priority in (High, Highest) AND resolution = Unresolved
project = GYM AND labels = needs-ac
assignee = currentUser() AND status != Done
```

Save useful queries as **filters** and share them or use them on dashboards.

## Real-world examples

| Team | Jira practice |
|---|---|
| E-commerce squad | Custom "Acceptance criteria" field required before a story can move to *Ready for Dev* |
| Bank | Components for each system (Payments, Accounts, Cards) so impact is easy to filter |
| Agency | Labels per client release; dashboard of open bugs per client |

## Step-by-step demonstration

**Scenario:** Create a story in Jira for "Cancel a booking".

1. **Open the project** "Gym Booking (GYM)".
2. Click **Create** (top bar).
3. **Issue type:** Story.
4. **Summary:** *Member can cancel a class booking.*
5. **Description:**
   > As a member, I want to cancel a class booking so that my place goes to someone else.
   >
   > **Context:** Today members phone reception to cancel; 30% of no-shows are people who forgot to call.
   >
   > **Acceptance criteria:**
   > 1. Member can cancel an upcoming booking from My bookings.
   > 2. Cancelling more than 2 h before start: status Cancelled, no penalty.
   > 3. Within 2 h: status Late cancellation; counts towards no-show limit; warning shown first.
   > 4. Place is offered to the first waitlisted member.
   > 5. Confirmation email sent within 5 minutes.
6. **Parent / Epic:** GYM-1 Online class booking.
7. **Priority:** High. **Labels:** `bookings`.
8. **Link** to the Confluence "Booking rules" page.
9. Click **Create** → Jira assigns **GYM-15**.
10. In refinement, the team adds **story points: 3** and moves it to *Ready for Dev*.

## Common mistakes

1. **Summary-only stories.** A one-line title isn't a requirement; add description and AC.
2. **Everything is a Task.** Use the right issue type so reporting works.
3. **Not linking to epics.** Orphan stories make progress invisible.
4. **Over-customising workflows.** Too many statuses slow everyone down.
5. **Using Jira instead of conversation.** Comments help, but talk to people for anything complex.
