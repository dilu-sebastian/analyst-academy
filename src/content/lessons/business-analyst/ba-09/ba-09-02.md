## Explanation

### From backlog to board

In a Jira **Scrum project**, the work lives in two main places:

| View | Purpose |
|---|---|
| **Backlog view** | Order, refine and plan items; create and start sprints |
| **Active sprint board** | Track work in progress during the sprint |

```
BACKLOG VIEW
┌ Sprint 4 (planned) ───────────────── 15 pts ─┐   [Start sprint]
│ GYM-12 Book a class                      5   │
│ GYM-15 Cancel a booking                  3   │
│ GYM-16 View my bookings                  2   │
│ GYM-18 Join waitlist                     5   │
└──────────────────────────────────────────────┘
┌ Backlog ─────────────────────────────────────┐
│ GYM-19 Waitlist offer notification       5   │  ← drag to reorder
│ GYM-22 Filter timetable by type          3   │
│ GYM-25 Check in by QR code               ?   │  ← not estimated yet
└──────────────────────────────────────────────┘

ACTIVE SPRINT BOARD
 To Do        │ In Progress   │ In Review    │ Done
 GYM-18       │ GYM-12        │ GYM-16       │ GYM-15
```

### Managing the backlog in Jira

| Task | How (typical) |
|---|---|
| **Order items** | Drag and drop in the backlog (sets *Rank*) |
| **Group by epic** | Use the Epics panel or group-by option |
| **Estimate** | Enter story points on each issue |
| **Flag readiness** | Use a status (*Ready for Dev*) or label (`ready`) |
| **Split a story** | Create new stories, move AC, link with *split from* or close the original |
| **Find gaps** | Quick filters: *No estimate*, *Needs AC*, *Unassigned epic* |
| **Clean up** | Close obsolete items regularly with a reason |

### Planning and running a sprint

1. **Create a sprint** in the backlog view.
2. During Sprint Planning, **drag top items** into the sprint until the team's capacity is reached (Jira shows total points).
3. **Start sprint**: set name, duration and **Sprint Goal**.
4. The team works on the **board**, moving cards across columns.
5. Developers add **sub-tasks** if helpful.
6. At the end, **Complete sprint**: Jira asks where to move unfinished items (next sprint or backlog).

### Board configuration basics

| Setting | Use |
|---|---|
| **Columns** | Map workflow statuses to board columns |
| **Swimlanes** | Group cards by epic, assignee, or query (e.g. expedite lane for urgent bugs) |
| **Quick filters** | One-click filters (e.g. *Only my issues*, *Bugs*) |
| **Card layout** | Show fields like story points or labels on cards |
| **WIP limits** (Kanban) | Maximum cards per column |

### Reports that BAs and POs use

| Report | Shows | BA use |
|---|---|---|
| **Burndown chart** | Remaining work in the sprint | Spot risk to the Sprint Goal early |
| **Velocity chart** | Points committed vs completed per sprint | Forecast how many sprints a feature needs |
| **Sprint report** | Completed, not completed, added mid-sprint | Discuss scope change in the retro |
| **Epic report / burnup** | Progress of an epic over time | Update stakeholders on feature progress |
| **Cumulative flow** (Kanban) | Items in each status over time | Find bottlenecks |

### Dashboards

A **dashboard** combines gadgets (filter results, pie charts, sprint health) for stakeholders. Example BA dashboard: *Open questions on stories*, *Stories without AC*, *Epic progress*, *Bugs by priority*.

### Kanban projects

For continuous flow (e.g. support teams), Kanban boards replace sprints. Key practices: visualise work, **limit WIP**, measure **cycle time**, and manage flow.

## Real-world examples

| Team | Practice |
|---|---|
| Payments squad | Expedite swimlane for production incidents; never more than 1 card in it |
| Product team | Quick filter "Needs PO decision" used in daily stand-ups |
| Support team | Kanban with WIP limit of 3 in *In Progress*; cycle time dropped from 6 to 3 days |

## Step-by-step demonstration

**Scenario:** Prepare and run Sprint 4 for the gym booking team.

**Two days before planning (BA + PO):**
1. In the backlog, apply quick filter *No estimate* → GYM-25 lacks points. Add it to the refinement agenda.
2. Apply filter `labels = needs-ac` → GYM-19 is missing AC. BA writes AC and removes the label.
3. Order the top 8 stories with Maria (PO) by dragging.

**Sprint Planning:**
4. Create **Sprint 4**. Team velocity ~15 points.
5. Drag GYM-12, 15, 16, 18 into the sprint (15 points).
6. Click **Start sprint**; goal: *Members can book, view and cancel classes, and join a waitlist.* Duration: 2 weeks.

**During the sprint:**
7. Daily Scrum around the board; BA checks the *In Review* column to help test.
8. Day 5: a bug (GYM-31) is found; tagged with the sprint only after PO agreement. Sprint report later shows it as *added mid-sprint*.

**Sprint end:**
9. **Complete sprint**: GYM-18 isn't done → moved to Sprint 5.
10. Review the **sprint report** and **burndown** in the retrospective.

## Practical example

Which Jira feature would you use?

| Need | Feature |
|---|---|
| Show stakeholders progress on the Online Booking epic | Epic report / burnup or dashboard |
| See only stories that still need acceptance criteria | Quick filter or saved filter (label `needs-ac`) |
| Highlight urgent production bugs on the board | Expedite swimlane |
| Forecast when the remaining 60 points will be done | Velocity chart |
| Limit the number of items being tested at once | WIP limit (Kanban) |

## Common mistakes

1. **Planning in Jira without talking.** The tool records decisions; the conversation makes them.
2. **Adding items mid-sprint without the PO.** It breaks focus and distorts reports.
3. **Never closing old items.** A 600-item backlog hides priorities.
4. **Misreading reports.** A flat burndown might mean the board isn't updated, not that no work happened.
5. **Too many columns.** Each extra status adds handoffs and admin.
