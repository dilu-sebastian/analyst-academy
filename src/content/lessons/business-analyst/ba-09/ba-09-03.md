## Explanation

### What is Confluence?

**Confluence** (also by Atlassian) is a team wiki: a place to create, organise and share documents. Where Jira tracks **work items**, Confluence holds the **knowledge** around them: requirements, process maps, decisions, meeting notes and business rules.

| Jira | Confluence |
|---|---|
| Stories, bugs, tasks | Requirements pages, specs, process documentation |
| Tracks status and progress | Explains context, rules and decisions |
| Short, structured fields | Rich pages: text, tables, diagrams, images |
| Changes constantly | More stable reference material (still living) |

### Structure: spaces, pages, page trees

| Concept | What it is | Example |
|---|---|---|
| **Space** | A container for a team, product or project | "Gym Booking Product" |
| **Page** | A single document | "Booking business rules" |
| **Page tree** | Parent-child hierarchy of pages | Requirements → Bookings → Cancellation rules |
| **Template** | Pre-built page layout | Product requirements, meeting notes, decision |
| **Labels** | Tags to group and find pages | `requirements`, `nfr`, `decision` |

### A typical BA space structure

```
Gym Booking Product (space)
├── Home: product vision, goals, team, key links
├── Discovery
│   ├── User research: interview summaries
│   └── Personas
├── Requirements
│   ├── Epic: Online class booking
│   │   ├── Business rules: booking and cancellation
│   │   └── Process map: as-is and to-be
│   ├── Epic: Waitlists
│   └── Non-functional requirements
├── Decisions log
├── Meeting notes
│   ├── Sprint reviews
│   └── Stakeholder workshops
└── Glossary
```

### Key Confluence features for BAs

| Feature | Use |
|---|---|
| **Templates** | Product requirements, decision record, meeting notes, retrospective |
| **Tables** | Business rules, data dictionaries, RACI |
| **Diagrams** | Embed draw.io/Lucidchart or Gliffy diagrams that stay editable |
| **Page properties + report** | Summarise metadata (status, owner) across many pages |
| **Status lozenges** | DRAFT, IN REVIEW, APPROVED badges |
| **Mentions (@)** | Ask a stakeholder to review a section |
| **Inline comments** | Discuss a specific sentence |
| **Page history** | Version control; compare and restore versions |
| **Watch / notifications** | Stay informed of changes |
| **Jira macros** | Embed live Jira issues or filters (next lesson) |

### Writing a good requirements page

A lean **product requirements page** typically has:

| Section | Content |
|---|---|
| **Header** | Epic, owner, status, target release, stakeholders |
| **Background / problem** | Why this matters, with evidence |
| **Goals and success metrics** | Outcomes, KPIs |
| **Assumptions** | What we believe is true |
| **Scope** | In / out |
| **User stories** | Table linked to Jira issues |
| **Business rules** | Numbered rules with examples |
| **Process / designs** | Diagrams, wireframes |
| **Questions** | Open questions with owner and outcome |
| **Not doing** | Explicit exclusions |

### Decision records

Capture significant decisions so the team remembers **why**:

| Field | Example |
|---|---|
| Decision | Late cancellations count as no-shows |
| Date | 12 March |
| Decided by | Maria (PO), Ops manager |
| Options considered | (1) No penalty, (2) fee, (3) count as no-show |
| Rationale | Fees need payment integration (out of scope); no-show count deters misuse |
| Impact | GYM-15, booking rules page |

## Real-world examples

| Team | Confluence practice |
|---|---|
| Insurance team | Every epic has one requirements page; Jira stories link back to it |
| Bank | Decisions log required by the change board for audit |
| Product start-up | Space home page with live roadmap and team contacts; onboarding time for new joiners halved |

## Step-by-step demonstration

**Scenario:** Create a requirements page for the "Waitlists" epic.

1. In the **Gym Booking Product** space, go to *Requirements*.
2. **Create** → choose the **Product requirements** template (or a team template).
3. Title: *Epic: Waitlists*. Set status lozenge **DRAFT**.
4. **Header:** Owner (BA), PO Maria, target Release 2, stakeholders: reception, instructors.
5. **Background:** *Popular evening classes fill within an hour; 25% of booked members don't attend. Members want a fair way to get freed places.*
6. **Goals:** Empty places in full classes down 40%; member satisfaction with booking ≥ 4/5.
7. **Business rules table:**

| ID | Rule | Example |
|---|---|---|
| WL-01 | Members may be on up to 3 waitlists | 4th attempt shows a message |
| WL-02 | Freed place offered to position 1 for 2 hours | Offer at 14:00 expires 16:00 |
| WL-03 | Within 2 h of class start, first waitlisted member is auto-booked | Class at 18:00, cancellation at 16:30 → auto-book |

8. **Diagram:** embed the BPMN waitlist process.
9. **Stories:** add a Jira table (next lesson) or list GYM-18, GYM-19.
10. **Questions:** *What if the auto-booked member can't attend?* Owner: Maria. Due: Friday.
11. @mention Maria and the ops manager for review; change status to **IN REVIEW**.
12. After agreement, set **APPROVED** and note the version in the page history.

## Practical example

Where should this information live: Jira or Confluence?

| Information | Where |
|---|---|
| "As a member, I want to join a waitlist..." with AC | Jira (story) |
| Full set of waitlist business rules with examples | Confluence (linked from stories) |
| Status of GYM-18 (In Progress) | Jira |
| Why we chose no-show counting instead of fees | Confluence (decision record) |
| Sprint review notes and stakeholder feedback | Confluence (feedback items then created in Jira) |
| Bug: offer email not sent | Jira |

## Common mistakes

1. **Pages nobody can find.** Use a clear page tree, labels and a good home page.
2. **Duplicating Jira content.** Link to Jira issues instead of copying them.
3. **Stale pages.** Show status and owner; review regularly; archive old pages.
4. **Walls of text.** Use headings, tables, diagrams and examples.
5. **Decisions lost in chat.** Record important decisions on a decisions page.
