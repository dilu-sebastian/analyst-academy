> **Prerequisites:** ba-09-03 Confluence for requirements documentation

## Explanation

### One story, two tools, zero copy-paste

Jira and Confluence are most powerful when **linked**: Confluence pages explain *why* and *what*, Jira issues track *doing*. Links in both directions mean anyone can jump from a story to its context, or from a requirements page to live delivery status.

```
 Confluence: Epic: Waitlists (requirements page)
 ├─ Business rules WL-01..WL-03
 ├─ Process diagram
 └─ [Jira issues macro: parent = GYM-17] ──► live list of stories + statuses
                                 ▲
                                 │ links both ways
                                 ▼
 Jira: GYM-18 Join waitlist ──► "Confluence pages: Epic: Waitlists"
```

### Ways to link

| Method | What happens |
|---|---|
| **Paste a Jira issue URL into Confluence** | Becomes a smart link showing key, summary and status |
| **Jira issues macro / Jira work item macro** | Embeds a single issue or a **live table** from a JQL query |
| **Create Jira issues from Confluence text** | Highlight requirement text → create issue; the issue links back automatically |
| **Link Confluence page from a Jira issue** | In the issue, add a web/Confluence link; Jira shows linked pages |
| **Jira roadmap / timeline macro** | Show epic progress on a Confluence page |
| **Jira charts macro** | Embed pie charts or created-vs-resolved charts |

*(Feature names vary by version; the capabilities are broadly the same.)*

### Live tables with JQL

On a requirements page, embed:

```
Jira macro query:  parent = GYM-17 ORDER BY rank
Columns:           Key, Summary, Status, Story points, Assignee
```

The table updates automatically. Stakeholders reading the page always see current delivery status, and you never maintain a manual list.

### A BA workflow that uses both

```
 1. Discovery notes             → Confluence (interview summaries)
 2. Requirements page per epic  → Confluence (rules, diagrams, scope)
 3. Highlight requirement → create stories → Jira (auto-linked)
 4. Refine stories (AC, points) → Jira
 5. Live story table on page    → Confluence (Jira macro)
 6. Sprint review notes         → Confluence; feedback items → Jira
 7. Decisions                   → Confluence decisions log, linked from Jira
 8. Release notes               → Confluence (Jira macro: fixVersion = 2.0)
```

### Traceability across tools

| Link | Answers |
|---|---|
| Confluence requirement ↔ Jira story | Which stories deliver this requirement? |
| Jira story ↔ test case (Xray/Zephyr) | Is it tested? Did it pass? |
| Jira story ↔ fixVersion | Which release includes it? |
| Decision record ↔ stories | Why does the story behave like this? |

This gives a lightweight **traceability matrix** without a separate spreadsheet (see ba-04-05).

### Release notes

Use **fixVersion** in Jira, then a Confluence release-notes template with a Jira macro: `fixVersion = "Release 2.0" AND type in (Story, Bug)`. Add a short human summary at the top for stakeholders.

### Good practice

- **Link, don't copy.** Duplicated text drifts out of sync.
- **One source of truth per item.** Stories in Jira; rules and context in Confluence.
- **Consistent naming.** Match epic names in both tools.
- **Permissions.** Make sure stakeholders who read Confluence can also see the linked Jira project (or they'll see "restricted" links).

## Step-by-step demonstration

**Scenario:** Connect the "Epic: Waitlists" Confluence page with Jira.

1. Open the approved **Epic: Waitlists** page.
2. Highlight the text *"Members can join a waitlist for a full class (up to 3)"*.
3. Choose **Create Jira issue** from the highlight menu → project GYM, type Story, parent GYM-17. Jira creates **GYM-18** and links it to the page.
4. Repeat for *"Freed places are offered to the first member for 2 hours"* → **GYM-19**.
5. In Jira, open GYM-18 and complete the description and AC, referencing rules WL-01 and WL-02 with a link to the page section.
6. Back on the page, insert a **Jira issues macro** with JQL `parent = GYM-17 ORDER BY rank`, showing Key, Summary, Status, Points.
7. Add the macro for the decision record page too, linking GYM-15 (cancellations).
8. At release, create **Release 2.0 notes** from the template with JQL `fixVersion = "2.0"`.
9. Check permissions: the ops manager can see both the space and the GYM project.

## Practical example

A stakeholder says: *"I read the requirements page but I have no idea if any of this is built yet."* What do you do?

1. Add a live **Jira issues macro** to the page showing stories and statuses.
2. Add an **epic progress** or roadmap macro at the top.
3. Make sure the stakeholder has Jira view permissions.
4. Optionally add a short "Delivery status" summary updated each sprint.

## Common mistakes

1. **Copying story text into Confluence.** Use live macros.
2. **Broken trails.** Stories with no link to context; pages with no link to stories.
3. **Permission gaps.** Stakeholders see "restricted" instead of the issue.
4. **Inconsistent names.** "Waitlist" epic in Jira vs "Queueing" page in Confluence confuses people.
5. **Dumping everything into Confluence.** Keep it curated: if it isn't maintained, archive it.
