## Explanation

### Miss a stakeholder, miss a requirement

A **stakeholder** is any person, group or organisation that **affects, is affected by, or believes they are affected by** a change. Forgetting one is one of the most common reasons projects fail: the payroll team who wasn't consulted, the regulator nobody thought of, the night-shift staff whose process breaks.

**Stakeholder identification** is the first step of stakeholder management, done at the start and **revisited throughout** the project.

### Categories of stakeholders

| Category | Examples |
|---|---|
| **Sponsor** | Funds and champions the change; final decisions |
| **Customers / end users** | People who use the product or service |
| **Internal users / operators** | Staff who run the process day to day |
| **Domain experts (SMEs)** | Know rules and detail of a business area |
| **Managers** | Responsible for affected teams |
| **Delivery team** | Developers, testers, architects, PM, PO |
| **Support / operations** | IT support, service desk, operations |
| **Regulators / compliance / legal** | Ensure laws and policies are followed |
| **Suppliers / partners** | Vendors, outsourced providers, integration partners |
| **Finance / procurement** | Budget, contracts, purchasing |
| **Unions / employee reps** | Represent staff affected by change |
| **The public / media** | For public services or high-profile changes |

**Internal vs external:**

```
                 ┌─────────── External ───────────┐
                 │ Customers  Regulators  Suppliers│
                 │   ┌───────── Internal ───────┐  │
                 │   │ Sponsor  Users  IT  Ops  │  │
                 │   │ Finance  Legal  HR       │  │
                 │   └──────────────────────────┘  │
                 └────────────────────────────────┘
```

### Techniques to identify stakeholders

| Technique | How |
|---|---|
| **Brainstorming** | Workshop with the sponsor and team: "Who is affected? Who can stop this?" |
| **Process mapping** | Every lane and handoff in the process is a stakeholder |
| **Organisation charts** | Find affected departments and managers |
| **Snowballing** | Ask every stakeholder: "Who else should I talk to?" |
| **Checklists** | Use the category list above |
| **Document review** | Contracts, policies and regulations name parties |
| **Onion diagram** | Circles from the core team out to the wider environment |

### The onion diagram

```
           ┌──────────────── Wider environment ────────────────┐
           │  Regulators, public, competitors                   │
           │   ┌────────────── Organisation ──────────────┐     │
           │   │  Sponsor, finance, other departments      │     │
           │   │   ┌──────── Affected units ─────────┐     │     │
           │   │   │  Users, managers, support        │     │     │
           │   │   │   ┌──── Solution delivery ──┐    │     │     │
           │   │   │   │  BA, PO, devs, testers  │    │     │     │
           │   │   │   └─────────────────────────┘    │     │     │
           │   │   └──────────────────────────────────┘     │     │
           │   └────────────────────────────────────────────┘     │
           └──────────────────────────────────────────────────────┘
```

### The stakeholder register

Record stakeholders in a **register** (a table):

| Name / Group | Role | Interest in the change | Influence | Impact on them | Attitude | Contact approach |
|---|---|---|---|---|---|---|
| Maria Lopez | Head of membership (Sponsor, PO) | Cut cancellations | High | Medium | Supportive | Weekly 1:1, reviews |
| Reception staff (6) | Booking operators | Fewer calls; job changes | Low | High | Mixed (worried) | Workshop, demos, training |
| Instructors (15) | Run classes | Attendee lists | Low | Medium | Neutral | Survey, review sessions |
| IT manager | Systems and security | Integration, support load | High | Medium | Cautious | Fortnightly check-in |
| Data protection officer | Compliance | Member data handling | High | Low | Neutral | Review of data requirements |

## Real-world examples

| Project | Missed stakeholder | Consequence |
|---|---|---|
| New HR system | Payroll team | Go-live delayed 2 months: export format didn't match payroll |
| Hospital app | Night-shift nurses | App assumed a pharmacy was open 24/7; it wasn't |
| Retail website | Customer service | Agents couldn't see online orders; complaints spiked |
| Council recycling change | Residents with disabilities | Assisted collection was dropped by mistake; public complaints |

## Step-by-step demonstration

**Scenario:** Identify stakeholders for a supermarket introducing self-checkout tills.

**Step 1: Brainstorm with the sponsor.** Store operations director (sponsor), store managers, cashiers, customers, security, IT, the till vendor.

**Step 2: Walk the process.** Customer scans → pays → age-restricted items need approval → exits past security. New stakeholders: **staff who approve age checks**, **loss prevention team**, **payment provider**.

**Step 3: Use the checklist.** Regulators? Yes: **licensing authority** (alcohol age checks). Finance? **Finance** for cash handling. Unions? **Shop workers' union** (job impact). Accessibility? **Disabled customers and an accessibility advocate**.

**Step 4: Snowball.** A store manager says: *"Talk to the cleaning contractor; the tills change floor layout."* Add **facilities**.

**Step 5: Build the register** with interest, influence, impact and attitude.

**Step 6: Review regularly.** At each phase, ask: *Who's new? Whose influence changed?*

## Practical example

Identify at least 8 stakeholders for a university moving all exams online:

Students, students with disabilities, lecturers, exam office, IT services, IT security, academic integrity / plagiarism team, student union, external examiners, accrediting bodies (e.g. professional regulators), exam software vendor, parents (indirectly), finance (licences), library (study spaces for students without devices).

## Common mistakes

1. **Only listing people you already know.** Use structured techniques and snowballing.
2. **Forgetting external and "invisible" stakeholders** like regulators, support teams and night shifts.
3. **Treating groups as one voice.** "Users" often contains different sub-groups with different needs.
4. **Identifying once and never again.** Stakeholders change over the life of a project.
5. **No record.** A register keeps knowledge visible and shareable.
